## 1. 项目定位

### 1.1 一句话定位

**gym-log 是一个面向个人健身者的训练记录与身体数据追踪应用——把训练计划落到「每一组」，把长期变化画成「看得懂的图」。**

### 1.2 三个核心场景

| 场景 | 用户的问题 | 对应功能 |
|---|---|---|
| **练之前** | 今天练什么？ | 今日训练卡片、计划模板库 |
| **练的时候** | 现在做哪组？歇多久？ | 跟练模式（M4） |
| **长期** | 三个月了我变强了吗？身体有变化吗？ | 数据可视化（M7） |

### 1.3 为什么做

- **定位**：求职作品集，主投 Java 后端岗。
- **业务复杂度**高于典型 CRUD 商城：周期化计划的展开算法、多态计量的组记录、指标聚合查询、离线优先与同步，都是能在面试里讲出技术取舍的点。
- **双端共用一套 REST API**，是后端能力最直接的展示位。

### 1.4 成功标准

V1 完成时，以下每一条都应当能被验证为「是」：

1. 能在真机上完整跟练一次训练（含组间休息计时），关掉 App 重开能续上，训练数据完整落库。
2. 能回答「深蹲这个动作，我最近三个月的力量变化如何」并画出曲线。
3. 修改已开始计划的第 3 周内容后，前 2 周的训练历史显示**完全不变**。
4. Flutter App 与 Vue Web 端访问**同一套 REST API**，无任何端专属接口。
5. 后端接口有 OpenAPI 文档，可直接演示。

## 2. 用户与场景

### 2.1 用户画像

**主要用户**：有一定训练经验的健身者（首先是自己）。

| 特征 | 说明 |
|---|---|
| 训练年限 | 半年以上，了解组、次、RM 等基本概念 |
| 训练频率 | 每周 2–5 次 |
| 使用环境 | 健身房，**手机信号通常较差** |
| 使用姿势 | 组间休息时单手操作手机，可能戴手套 |
| 核心诉求 | 不想用纸笔记录；想知道自己有没有进步 |

**明确不考虑的用户**（V1）：零基础小白（需要动作教学而非记录）、专业教练（需要学员管理）、健身房运营方。

### 2.2 场景走查

#### 场景 A：制定计划（首次使用）
> 用户注册登录 → 浏览内置计划模板库 → 选择「推拉腿 PPL（每周 3 练）」→ 系统按模板生成计划 → 用户调整其中某个动作的重量 → 开始执行。

#### 场景 B：练之前
> 用户到健身房，打开 App → 首页显示「今天：推日（Push A）」→ 点「开始训练」→ 进入跟练模式。

#### 场景 C：练的时候（核心场景）
> 跟练模式显示「卧推 第 1 组 / 共 4 组，目标 8 次，建议 60kg」→ 用户做完，点「完成本组」→ 自动开始 90 秒组间休息倒计时 → 用户可 ±15 秒调整或跳过 → 倒计时结束，提示音 + 语音播报「休息结束，下一组 卧推 8 次」→ 继续。
>
> **全程单手可操作**，且**屏幕不能自动熄灭**。

#### 场景 D：练之后
> 训练结束 → 显示总结（总时长 62 分钟、总容量 8,450kg、卧推创 PR）→ 数据同步到云端。

#### 场景 E：长期回顾
> 三个月后，用户在 PC 上打开 Web 端 → 看体重 7 日移动平均曲线（下降 3.2kg）→ 看深蹲估算 1RM 曲线（上升 15kg）→ 看肌群周**组数**柱状图（发现背部组数偏低，只有 8 组/周）→ 调整计划。

## 3. 术语表

> **本节的每个词都写「本项目采用的定义」，而非通用词典释义。** 术语不统一，后面全是歧义。
> 本文档后续章节及 [METRICS.md](./METRICS.md) 中出现的领域词，以本节为准。

### 3.1 训练基本单位

| 术语 | 本项目定义 |
|---|---|
| **动作（Exercise）** | 一个可独立计量的训练动作，如「杠铃卧推」。动作库中的一条记录。 |
| **组（Set）** | 连续完成若干次动作的一个单元。训练记录的最小单位。 |
| **次（Rep）** | 组内完成一次完整动作。 |
| **组间休息（Rest）** | 两组之间的间歇时长。本项目以**秒**为单位存储。 |
| **热身组（Warmup Set）** | 为正式组做准备的轻重量组。`set_type = warmup`。 |
| **正式组（Working Set）** | 真正计入训练量的组。**默认所有统计只计正式组**。 |
| **力竭组（Failure Set）** | 做到无法再完成一次标准动作的组。`set_type = failure`。 |
| **递减组（Drop Set）** | 一组做到力竭后立即减重继续做。`set_type = drop`。 |
| **超级组（Superset）** | **两个动作背靠背交替执行，组内动作之间不休息**，一轮做完才休息。例：A1 卧推 → A2 划船 → 休息 90s → A1 → A2 → 休息…… |
| **三合组 / 巨型组（Triset / Giant Set）** | 超级组的推广形式：三个及以上动作轮转。本项目**统一用「超级组」泛指**，动作个数由 `group_size` 表示。 |

### 3.2 强度与计量

| 术语 | 本项目定义 |
|---|---|
| **1RM** | 只能完成 1 次的最大重量。**实测 1RM 有受伤风险，本项目不要求用户实测。** |
| **估算 1RM（e1RM）** | 由正式组的重量和次数反推的 1RM 估计值。本项目采用 **Epley 公式：`e1RM = w × (1 + r/30)`**，仅当 `r ≤ 12` 时参与计算。用于把不同重量×次数的组换算成可比的力量指标。 |
| **%1RM** | 训练重量占 1RM 的百分比。表现强度的指标。 |
| **RPE** | 主观用力程度，1–10 分。本项目采用常见的力量训练标度：RPE 8 表示「还能再做 2 次」。 |
| **RIR** | 剩余次数（Reps In Reserve）。`RIR = 10 − RPE`。与 RPE 二选一即可，本项目**存储 RPE**。 |
| **计量类型（metric_type）** | 动作的计量方式判别器。见 3.4。 |

### 3.3 训练量与强度

| 术语 | 本项目定义 |
|---|---|
| **训练容量（Volume）** | **本项目口径：仅统计正式组，`Σ(重量 × 次数)`。** 自重动作按 `Σ(体重 × bw_factor × 次数)` 计算（见 3.4）。热身组**不计入**。口径必须全局统一，否则所有趋势图失真。 |
| **组数（Sets）** | 正式组的数量。**与容量是两个独立指标，不可互相替代**：容量反映总负荷变化，组数用于**跨肌群比较**。肌群之间重量不可比——卧推 80kg 与侧平举 10kg 的 `重量×次数` 差 6 倍，画在同一张图上小肌群会被压成看不见的线。运动科学文献讨论「每周 10–20 组」时用的就是组数。详见 [METRICS.md](./METRICS.md) 第 4 节。 |
| **强度（Intensity）** | 本项目指 `平均 %1RM` 或 `平均 RPE`，用于与容量搭配解读。**容量涨 ≠ 进步**，可能只是休息变长、强度下降。 |
| **渐进超负荷** | 逐步增加重量、次数或组数以持续制造训练刺激。本项目的核心追踪目标。 |
| **deload** | 主动降低强度/容量的恢复周（通常 −40% 左右）。周期化计划的一部分，**不算作未完成计划**。 |
| **周期化（Periodization）** | 把长期计划划分为若干周，每周强度不同（递增或波动）。 |

### 3.4 计量类型（metric_type）

一个动作的计量方式，决定 `SetRecord` 上哪几个字段有意义。

| metric_type | 有意义的字段 | 举例 |
|---|---|---|
| `weight_reps` | `weight`, `reps` | 杠铃卧推、哑铃弯举 |
| `reps_only` | `reps` | 引体向上、俯卧撑 |
| `duration` | `duration_sec` | 平板支撑、死吊 |
| `distance_duration` | `distance_m`, `duration_sec` | 跑步、划船机 |

**自重动作的容量计算（`bw_factor`）**：`reps_only` 动作若为自重负荷，只有次数无法与负重动作比较容量。为每个此类动作定义 **`bw_factor`（体重系数）**，容量按 `体重 × bw_factor × 次数` 计算：

| 动作 | `bw_factor` 参考值 |
|---|---|
| 引体向上 / 双杠臂屈伸 | 1.0 |
| 倒立撑 | 0.9 |
| 俯卧撑 | 0.65 |
| 反向划船 | 0.55 |
| 臀桥 / 平板支撑 | 0.5 |

系数在动作库中**可编辑**，上表默认值来自常见生物力学估算，仅供参考。会话创建时**快照当时的体重**，保证历史容量可重算。

> **设计决策**：`SetRecord` 同时持有 `weight / reps / duration_sec / distance_m` 四个**可空**列，由 `Exercise.metric_type` 决定哪个有意义。
> **不用 EAV**（「取最近 10 次最佳组」这类查询会变成噩梦），也**不为每种类型建表**（JOIN 爆炸）。新增计量方式（如负重引体）只需加列。

### 3.5 计划与执行

| 术语 | 本项目定义 |
|---|---|
| **计划（Program）** | 一个长期训练安排，如「8 周增肌计划」。含总周数、每周频率、训练日结构。 |
| **训练日模板（DayTemplate）** | 计划中的一个训练日结构，如「推日 A」。含若干处方动作。 |
| **处方（PrescribedExercise）** | 训练日模板中的一个动作及其目标：目标组数、次数区间、目标重量、组间休息。 |
| **训练会话（Session / WorkoutSession）** | **某天实际执行的一次训练**。由训练日模板生成，但**独立于模板**。 |
| **组记录（SetRecord）** | 实际完成的某一组。属于某个训练会话。 |
| **跟练模式** | 按计划顺序逐动作、逐组引导用户执行，并管理组间休息计时的界面模式。 |
| **快照（Snapshot）** | 会话创建时对处方值的**深拷贝**。见 6.3 不变量。 |

### 3.6 进度指标

| 术语 | 本项目定义 |
|---|---|
| **出勤率** | `完成场次 / 计划场次`。**只看去没去，不看练得对不对**。反映习惯。 |
| **符合率** | `Σ min(实际完成, 计划目标) / Σ 计划目标`，**仅统计 exercise_id 匹配的组**，分子做 clamp 防止超 100%。反映执行度。 |
| **PR（个人纪录）** | 某动作在重量、次数或估算 1RM 上的历史最好成绩。 |

> **设计决策**：出勤率与符合率**必须是两个指标**。合成一个会被「练了但没按计划」污染——用户临时改动作、加组、减重量，在出勤率里算成功，在符合率里算偏差，但**都不该算失败**。临场调整是正常训练行为。

## 4. 范围与非目标

> **明确写出「不做什么」和理由。** 没有边界的需求文档等于没有需求文档。

### 4.1 V1 明确不做

| 不做 | 理由 | 未来触发条件 |
|---|---|---|
| 社交 / 排行榜 / 动态 | 个人工具，无社交需求；且引入内容审核负担 | 有 ≥50 名活跃用户时重新评估 |
| **完整食物库 / 条码扫描 / 营养素细分** | 食物数据库体量极大（中国食物成分表需购买或手工整理数百条），且与后端岗要展示的技能无关。**V1 只做轻量饮食记录，见 M11** | 有真实用户反馈「记总热量不够用」时 |
| 问卷式自动生成计划 | 规则引擎调参成本高，且生成的计划质量难以验证 | 内置模板库被用尽且用户主动要求时 |
| **AI 生成 / 调整训练计划** | 见下方专述。**这是明确的高风险项**，不是能力问题 | 不设触发条件 |
| AI 生成训练**建议**（低风险场景） | — | **V1 做，见 M12** |
| 视频动作识别 / 计数 | 需要 CV 模型与大量标注数据，与后端岗定位无关 | 不设触发条件 |
| 可穿戴设备深度集成 | 各厂商 SDK 割裂，国内数据开放度低 | 有统一开放平台时 |
| 教练端 / 学员管理 | 面向个人用户，不是 SaaS | 不设触发条件 |
| 课程 / 教学视频 | 本项目是**记录工具**，不是教学平台 | 不设触发条件 |
| 离线冲突自动合并（CRDT） | 单用户多设备并发编辑同一会话的概率极低 | 出现真实冲突投诉时 |

### 4.2 V1 不做但预留

| 项 | 预留方式 |
|---|---|
| 对象存储（OSS） | 体态照片 V1 存本地磁盘，但存储层抽象为接口，换 OSS 不改业务代码 |
| Redis 缓存 | 不引入。JWT 无状态 + MySQL 存 refresh token 足够。指标查询先走 MySQL 索引优化 |
| 第三方登录 | 用户表预留 `provider` / `provider_user_id` 字段，V1 只实现 `local` |
| 多角色扩展 | V1 只有 `USER` / `ADMIN` 两个角色，但权限表按 RBAC 设计（见 M10），加角色不改表结构 |
| **计划版本化** | `Program` 保留 `version` / `root_id` 字段，但 V1 不做版本复制。会话快照已保证历史数值正确，版本化的剩余价值（查看历史结构、回滚）不足以抵消成本。见 6.3 不变量 2 |
| **`%1RM` / `RPE` 目标重量** | 数据结构已支持（`target_weight_type` 三值），但展开算法 V1 只实现 `ABSOLUTE`。另两个遇到会明确报错，等 Phase 4 有了 e1RM 数据再补 |

### 4.3 为什么 AI 不生成计划 —— 专述

用户已确认 V1 接入 AI（低风险场景）。**但「生成训练计划」这一项明确不做**，理由不是能力问题：

1. **输出必须结构化且可校验。** 模型返回自然语言，要落库就得定义 JSON Schema、做校验、处理不守格式的情况、重试。这部分工作量远超「调用 API」本身。
2. **必须有安全兜底。** 模型会生成「深蹲 200kg 做 5×5」这类不合理处方。要拦截就得写规则层——**而这个规则层本身就是「计划生成引擎」**。等于写了两遍，且第二遍才是真正有价值的那一遍。
3. **面试视角是负分。** 面试官会问「为什么用 AI」。答「自动生成计划」很弱——**项目已经有模板库了**，模板库解决 90% 需求，AI 解决最后 10% 却要 10 倍成本，且引入不可控风险。
4. **训练计划出错会伤人。** 这不是「推荐错了重来」的场景。

**V1 的 AI 只做「解释与总结」，不做「决策与生成」**——见 M12。

### 5.2 技术选型

| 层 | 选型 | 理由 |
|---|---|---|
| 后端框架 | Spring Boot 3.x | JDK 17 满足要求；生态成熟 |
| 持久层 | MyBatis-Plus | 已有使用经验；复杂聚合查询比 JPA 更可控 |
| 数据库 | MySQL 8.0 | 本机已装并运行 |
| 鉴权 | Spring Security + JWT | 无状态，双端友好 |
| 数据库迁移 | Flyway | 版本化 DDL，比手写 SQL 脚本专业 |
| 接口文档 | springdoc-openapi | 自动生成 Swagger UI，可直接演示 |
| 客户端 | Flutter 3.x + Dart 3 | 一套代码出双平台 |
| 客户端状态管理 | Riverpod | 编译期安全，测试友好 |
| 客户端本地存储 | drift (SQLite) | 离线优先的落地基础 |
| 客户端图表 | fl_chart | Flutter 生态最成熟的图表库；移动端图表按 M7-B 单独设计，**不照搬 PC 端方案** |
| Web 端 | Vue 3 + Vite + TypeScript | 国内 Java 岗最常见组合 |
| Web UI 组件 | Element Plus | 后台型界面开发效率高 |
| Web 图表 | ECharts | 国内标准，图表类型全 |
| 权限模型 | Spring Security + RBAC 三表 | 面试高频考点，见 M10-A |
| LLM 调用 | Spring WebClient（封装为 `LlmClient` 接口） | 实现可替换，见 Q11 |
| 对象存储 | V1 本地磁盘，接口抽象 | 换 OSS 不改业务代码 |

### 5.3 双端共用一套 API

**核心约束**：Flutter App 与 Vue Web **访问完全相同的 REST API**，不存在端专属接口。

含义：
- 接口设计以**领域资源**为中心（`/api/v1/sessions`），不以**页面**为中心（`/api/v1/today-page`）。
- 分页、排序、筛选参数在两端语义一致。
- Web 端需要而 App 端不需要的数据（如长周期聚合），通过**同一接口的不同查询参数**获得，不新建接口。

### 5.4 离线优先策略

**背景**：健身房信号差，跟练时每记一组都打接口，体验会崩。

**分级**：

| 能力 | 离线可用性 | 说明 |
|---|---|---|
| 跟练记录 | **完全离线** | 写本地 SQLite，训练结束后批量同步 |
| 查看今日计划 | **完全离线** | 提前缓存 |
| 查看历史记录 | 只读离线 | 缓存最近 N 次 |
| 身体数据录入 | 离线可写 | 进同步队列 |
| 图表 / 统计 | 需要在线 | 聚合计算在后端 |
| 账号相关 | 需要在线 | — |

**同步策略**：会话结束时批量上传。客户端为每条记录生成 UUID 作为幂等键，后端按 UUID 去重，重复上传不产生脏数据。

### 5.5 不引入 Redis 的理由

JWT 是无状态的，不需要 session 存储；refresh token 存 MySQL 即可。指标聚合查询先用索引优化，V1 的数据量（单用户数千条组记录）远达不到需要缓存的规模。**为了用而用中间件是负分**——面试官会问「为什么需要 Redis」，答不上来不如不用。

| `WeekTemplate` | 计划的周结构（强度修饰） |
| `DayTemplate` | 训练日模板 |

### 6.2 关系主线

```
Program ──< WeekTemplate ──< DayTemplate ──< PrescribedExercise >── Exercise
   │                                              │
   │ 展开（创建会话时深拷贝为快照）                  │
   ▼                                              ▼
WorkoutSession ──< SessionExercise ──< SetRecord >── Exercise
                                            │
                                            └──> PersonalRecord（触发更新）
```

**单向流动，永不回写。**

### 6.3 关键不变量

> 这三条是数据模型的地基，违反任何一条都会导致历史数据错误。

**不变量 1：历史会话不受计划变更影响。**
`WorkoutSession` 创建时，把 `PrescribedExercise` 的处方值**深拷贝**到 `SessionExercise`。此后用户修改计划，已创建的会话及其快照**不变**。

- 反例：若会话只存 `prescribed_exercise_id` 外键，用户第 5 周改了训练日的动作，前 4 周的历史会显示成改后的样子。
- 用户想「以后都按这个来」时，**直接改计划结构**（V1 不做版本 promote，见不变量 2）——
  改动只影响未来的会话，已经快照过的历史不受任何影响。

**不变量 2：计划结构可以自由修改，历史记录不受影响 —— 靠的是会话快照，不是版本化。**

> ⚠️ **2026-09-17 修订**：本条原本定义为「计划改动产生新版本号」，
> 实现阶段重新评估后**降级**。理由如下。

`Program` 保留 `version` / `root_id` 字段，但 **V1 不做版本复制**——
用户修改计划结构时直接改原记录。

**为什么这个取舍是安全的**：不变量 1 已经把所有风险挡掉了。
会话在创建时对处方做了深拷贝，所以用户之后**怎么改计划，
历史训练记录的数值都不受影响**：

```
用户第 5 周改第 6-8 周的动作
→ 第 1-4 周的会话早已快照了自己的处方值
→ 历史记录显示「当时卧推目标 60kg」，不会被改成 65kg
```

**版本化真正剩下的价值只有两条**：

| 场景 | 强度 |
|---|---|
| 查看「改之前的计划长什么样」 | 低——用户自己记得练了什么 |
| 回滚到旧版本 | 中——改错了想恢复 |

而完整版本化的**成本不低**：复制整个计划（8 周约 100 条记录）、
定义「新版本从第几周生效」、处理「会话指向已归档计划」的边界、
列表和详情都要区分版本。

**对个人应用，这个取舍不划算。** 字段保留，将来真需要时随时能补，不用改表。

> **⚠️ 实现约束（2026-09-17，步骤 2.14 定下）**：
> 计划结构编辑采用**全量替换**（删掉所有子记录再重建），
> 因此 `day_template.id` / `prescribed_exercise.id` **每次编辑都会变**。
>
> 这直接推出会话快照的一条硬性规则：
> **`SessionExercise` 不得以外键引用 `day_template` / `prescribed_exercise`。**
> 它必须存**值**（`programId` + `dayNumber` + `dayName` + 动作名 + 处方数值），
> 而不是存指向结构表的 id。
>
> 只存 `prescribed_exercise_id` 的话，用户改一次计划，
> 全部历史会话的快照就指向了不存在的行——不变量 1 会被绕过，
> 而且这次的绕过**不会有任何报错**，只是历史显示成空白。

> **这条修订本身值得记住**：原定义的前提是「不做版本化会把历史改错」，
> 但那个前提在**会话快照**设计下不成立。
> 需求评审时要检查的正是这种「前提已被其他设计消解」的条目。

**不变量 3：组记录永不回写模板。**
`SetRecord` 只属于 `WorkoutSession`。用户临场改重量、加组、换动作，**只影响本次会话**，不会污染计划模板。

### 6.4 周期化的建模

**问题**：8 周 × 每周 3 练 = 24 个训练日。手写 24 个 `DayTemplate` 不可维护。

**方案**：结构 × 强度修饰分离。

- `DayTemplate` 定义**结构**：推日 A / 拉日 A / 腿日 A（共 3 个）
- `WeekTemplate` 定义**强度修饰**：第 1–4 周 +0%、第 5–7 周 +5%、第 8 周 deload −40%（共 8 个）

**处方值在会话创建时展开计算**，结果写入快照。模板只存 3 + 8 = 11 条记录，而非 24 条。

### 6.5 计量多态

见 3.4。`SetRecord` 用**宽字段 + 判别器**：

```sql
-- 示意，非最终 DDL
CREATE TABLE set_record (
  id            BIGINT PRIMARY KEY,
  session_exercise_id BIGINT NOT NULL,
  set_index     INT NOT NULL,
  set_type      ENUM('warmup','working','failure','drop') NOT NULL DEFAULT 'working',
  weight        DECIMAL(6,2)  NULL,   -- metric_type = weight_reps
  reps          SMALLINT      NULL,   -- weight_reps / reps_only
  duration_sec  INT           NULL,   -- duration / distance_duration
  distance_m    DECIMAL(8,2)  NULL,   -- distance_duration
  rpe           DECIMAL(3,1)  NULL,
  rest_actual_sec INT         NULL,
  completed_at  DATETIME      NOT NULL
);
```

**volume 是派生值**，不入库（或入库时绑定口径版本号），避免口径变更后历史数据无法重算。

### 6.6 超级组的建模

**结构**：超级组是 `PrescribedExercise` 上的一个**分组标记**，不是独立实体。

```
PrescribedExercise:
  ...
  superset_group   INT NULL      -- 超级组编号，NULL 表示单独动作
  order_in_group   INT NULL      -- 组内顺序（1, 2, 3...）
  group_size       INT NULL      -- 冗余字段，组内动作总数（便于查询与校验）
```

**约束**：同一 `DayTemplate` 内，`superset_group` 相同的记录构成一个超级组；`order_in_group` 唯一。

**执行语义**（关键，决定了状态机复杂度）：

| 位置 | 是否有组间休息 |
|---|---|
| 超级组**内部**的动作之间 | **无休息**，直接进入下一个动作 |
| 超级组**一轮完成**之后 | 有休息（取组内最长的 `rest_sec` 或用户设定） |
| 单独动作（`superset_group = NULL`） | 行为与原来完全一致 |

**训练容量的影响**：超级组不影响容量口径——每个动作的组照常计算 `重量 × 次数`，只是执行顺序变了。

**不变量 4（新增）：超级组的分组在会话快照中固化。**
用户在会话进行中把某两个动作临时组成超级组，只影响**本次会话**（写入 `SessionExercise`），不回写 `DayTemplate`。理由同不变量 3。

| 编号 | 需求 | 优先级 |
|---|---|---|
| M4-E-1 | **屏幕常亮**（Wake Lock） | Must |
| M4-E-2 | **断点续训**：杀进程重开能恢复到中断位置 | Must |

| M4-E-6 | 耳机线控 / 媒体播放键映射为「完成本组」 | Could |
| M4-E-7 | **音频不得抢占其他 App 的媒体播放**：用户用网易云/QQ音乐放歌时，本 App 的提示音必须**混入**而非**打断**——不能暂停音乐，不能压低音量，不能夺取音频焦点 | Must |
| M4-E-8 | 语音播报同样不得打断音乐（需要单独配置 TTS 的音频会话类别） | Must |
| M4-E-9 | 若系统处于静音/勿扰模式，降级为震动（Android）或触觉反馈 | Should |

> **M4-E-7 是硬性要求，不是优化项。** 健身房里绝大多数人戴着耳机听歌训练，如果 App 的提示音每 90 秒打断一次音乐，用户会直接卸载。
>
> **实现要点**：
> - **Android**：音频属性使用 `USAGE_ASSISTANCE_SONIFICATION` + `CONTENT_TYPE_SONIFICATION`，并**显式设置不申请音频焦点**（`AudioFocus.none`）。系统会把这类音频当作「辅助提示音」与媒体流混音。
> - **iOS**：`AVAudioSession` 类别设为 `.ambient`，或使用 `.playback` 并加 `.mixWithOthers` 选项。
> - **TTS 要单独配**：`flutter_tts` 默认使用 `.playback` 类别，会打断音乐，必须显式设置音频类别。**这一条最容易被漏掉**，因为提示音配好了，语音播报仍然会打断音乐。
>
> 详细规格见 [TIMER-SPEC.md](./TIMER-SPEC.md) 第 3.4 节。

### M10 管理后台（Must）

> **对 Java 后端岗的定位**：管理后台是**面试价值最高的模块之一**。RBAC 权限模型、审计日志、数据看板，都是面试高频考点，且比业务 CRUD 更能体现设计能力。

| 编号 | 需求 | 优先级 |

| M10-A-1 | 角色表、权限表、用户角色关联表——**标准 RBAC 三张表**，而非在用户表上加 `is_admin` 布尔字段 | Must |

| M10-D-4 | 重置用户密码（生成临时密码，不查看原密码——原密码是 BCrypt 哈希，本就不可逆） | Should |
| M10-D-5 | 删除用户（**二次确认 + 级联删除其所有数据**） | Must |

| M10-E-4 | 动作使用频率排行（哪些动作最常被练） | Could |

### M11 饮食记录（轻量版，Should）

> **范围界定**：只记**总热量**与**蛋白质**两个数，**不做食物库、不做条码扫描、不做营养素细分**。理由见 4.1。

| 编号 | 需求 | 优先级 |
|---|---|---|
| M11-1 | 每日录入**总热量**（kcal）与**蛋白质**（g） | Must |
| M11-2 | 设定每日目标值，显示完成进度 | Must |
| M11-3 | **快速复制昨日数据**（多数人饮食重复度高） | Should |
| M11-4 | 与**体重趋势关联**：热量缺口 vs 体重变化的实际对照，用于校准估算的 TDEE | Should |
| M11-5 | 与**训练量关联**：训练日的热量/蛋白摄入对比 | Could |
| M11-6 | 按周 / 月的热量与蛋白质达标率 | Should |
| M11-7 | 记录备注（如「聚餐」「欺骗餐」） | Could |

> **M11-4 是轻量版真正的价值点**。市面上的 TDEE 计算器都是公式估算，误差可达 ±300 kcal。记录两周「实际摄入 vs 实际体重变化」后反推出的 TDEE，比任何公式都准。**两个数就够做这件事**，不需要食物库。

### M12 AI 辅助（低风险场景，Should）

> **边界**：AI 只做「**解释与总结**」，**不做「决策与生成」**。理由见 4.3。

| 编号 | 需求 | 优先级 |
|---|---|---|
| M12-1 | **训练总结生成**：把本次训练的客观数据转成一段自然语言总结 | Must |
| M12-2 | **进度解读**：根据近期数据生成一句观察（如「深蹲连续三周停滞，可能与睡眠不足相关」） | Should |
| M12-3 | **自动填写训练备注**：根据当天的 RPE、组数完成情况生成备注草稿，用户可编辑 | Should |
| M12-4 | **AI 功能必须可完全关闭**（设置项），关闭后不发起任何请求 | Must |
| M12-5 | **所有 AI 输出必须标注「由 AI 生成」**，且**不得**给出医疗、伤病、用药建议 | Must |
| M12-6 | AI 输出**不落库为主数据**——只作为展示或用户确认后的备注 | Must |
| M12-7 | 每次调用记录 `AiSuggestion`：用户、场景、输入摘要、输出、时间，便于追溯 | Should |
| M12-8 | 明确的免责声明：AI 建议不构成训练或医疗指导 | Must |
| M12-9 | 调用失败时静默降级，不阻塞主流程 | Must |

> **M12-5 与 M12-6 是不可让步的**。AI 输出直接写进训练记录会污染数据，且一旦模型产生幻觉（如「你的膝盖疼痛建议停止深蹲」），用户可能当真。**AI 的输出必须经过用户确认才能进入数据。**
>
> **技术实现**：后端用 `WebClient` 调用 LLM API，Prompt 与输出解析放在独立 Service 中，配超时、限流与降级。**不在客户端直接调用**——API Key 不能下发到客户端。

## 10. 迭代路线图

> 延续 mini_mall 的混合协作模式：
> - **【用户写】** 核心的、面试要考的部分 —— 先给规格和提示，卡住再介入
> - **【Claude 写】** 模板性代码 —— 实体类、Mapper、DTO/VO、Controller 骨架、前端页面、配置

### Phase 0 —— 环境搭建
Flutter SDK、Android Studio、Android SDK、真机调试、项目骨架
**产出**：`flutter run` 能在真机上跑起 demo

### Phase 1 —— 后端地基
用户注册登录、JWT 双 token、Spring Security 配置、**RBAC 三张表建好（角色关联接上，权限校验后置）**、Flyway 迁移、统一响应封装、异常处理、Swagger
**【用户写】** `JwtUtil`、`JwtAuthenticationFilter`、双 `SecurityFilterChain`
**产出**：能注册登录，拿到 token 访问受保护接口

### Phase 2 —— 动作库与计划管理
内置动作库种子数据（含 `metric_type` 与 `bw_factor`）、自定义动作、计划 CRUD、**6 个内置模板（力量 / 分化 / 徒手）**、**逐组处方**、**超级组配置**、**周期化展开算法**、计划结构编辑
**【用户写】** 周期化展开算法（`DayTemplate × WeekTemplate → 处方值`）+ 超级组校验（组内顺序唯一性）
**产出**：能创建计划（含超级组与徒手计划）并查询「今天练什么」

### Phase 3 —— 跟练（核心，**工作量最大**）
会话创建与快照、组记录 CRUD、跟练状态机、**超级组执行**、**音频隔离**、本地 SQLite、离线队列、断点续训
**【用户写】** 跟练状态机 + 会话快照的深拷贝逻辑 + 超级组的轮次推进逻辑
**产出**：真机上完整跟练一场（含超级组）并落库，全程音乐不被打断

> ⚠️ **超级组让这个 Phase 的工作量接近翻倍**。状态机从「一个动作做完全部组」变成「动作可分组轮转」，`exercising → setDone` 之后要判断「组内还有动作吗 / 还有下一轮吗」，两个维度都要推进。持久化结构也要加 `currentRound` 和 `currentExerciseInGroup`。
>
> **建议**：先实现不带超级组的顺序执行跑通（1–2 天），确认状态机和断点续训稳定，**再叠加超级组**。一次性写完会很难定位 bug。

### Phase 4 —— 身体数据与可视化
身体测量（体重/围度）、体成分、生理指标、主观状态、体态照片、指标聚合接口、图表接口、**手机端图表（fl_chart，按 M7-B 适配）**
**【用户写】** 指标聚合的 SQL（移动平均、估算 1RM、容量与组数的分组统计）
**产出**：能回答「三个月有没有变强 / 身体变了没有」，且**在手机上能查单动作历史**

### Phase 5 —— Web 端（用户端）
Vue 3 项目搭建、登录、计划管理、图表页（ECharts，含 PC 专属的多序列图与双轴图）
**产出**：PC 上能看完整长期趋势——这是手机端刻意做不到的那部分

### Phase 6 —— 管理后台
**【用户写】** RBAC 三表设计 + `@PreAuthorize` 方法级鉴权 + 审计日志切面
**产出**：管理员能维护动作库与模板、管理用户，所有写操作有审计记录

> **RBAC 建议放在 Phase 6 而非 Phase 1**：它的三张表要在 Phase 1 就建好（`User` 关联 `UserRole`），但完整的权限体系、管理端接口、审计日志可以晚做。**不要在还没跑通业务时先花时间雕花权限系统。**

### Phase 7 —— 饮食与 AI（可选）
