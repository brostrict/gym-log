## 1. 项目定位

### 1.1 一句话定位

**gym-log 是一个面向个人健身者的训练记录与身体数据追踪应用——把训练计划落到「每一组」，把长期变化画成「看得懂的图」。**

### 1.2 三个核心场景

| 场景 | 用户的问题 | 对应功能 |
|---|---|---|
| **练之前** | 今天练什么？ | 今日训练卡片、计划模板库 |
| **练的时候** | 现在做哪组？歇多久？ | 跟练模式（M4） |
| **长期** | 三个月了我变强了吗？身体有变化吗？ | 数据可视化（M7） |

### 1.3 为什么做

- **定位**：求职作品集，主投 Java 后端岗。
- **业务复杂度**高于典型 CRUD 商城：周期化计划的展开算法、多态计量的组记录、指标聚合查询、离线优先与同步，都是能在面试里讲出技术取舍的点。
- **双端共用一套 REST API**，是后端能力最直接的展示位。

### 1.4 成功标准

V1 完成时，以下每一条都应当能被验证为「是」：

1. 能在真机上完整跟练一次训练（含组间休息计时），关掉 App 重开能续上，训练数据完整落库。
2. 能回答「深蹲这个动作，我最近三个月的力量变化如何」并画出曲线。
3. 修改已开始计划的第 3 周内容后，前 2 周的训练历史显示**完全不变**。
4. Flutter App 与 Vue Web 端访问**同一套 REST API**，无任何端专属接口。
5. 后端接口有 OpenAPI 文档，可直接演示。

## 2. 用户与场景

### 2.1 用户画像

**主要用户**：有一定训练经验的健身者（首先是自己）。

| 特征 | 说明 |
|---|---|
| 训练年限 | 半年以上，了解组、次、RM 等基本概念 |
| 训练频率 | 每周 2–5 次 |
| 使用环境 | 健身房，**手机信号通常较差** |
| 使用姿势 | 组间休息时单手操作手机，可能戴手套 |
| 核心诉求 | 不想用纸笔记录；想知道自己有没有进步 |

**明确不考虑的用户**（V1）：零基础小白（需要动作教学而非记录）、专业教练（需要学员管理）、健身房运营方。

### 2.2 场景走查

#### 场景 A：制定计划（首次使用）
> 用户注册登录 → 浏览内置计划模板库 → 选择「推拉腿 PPL（每周 3 练）」→ 系统按模板生成计划 → 用户调整其中某个动作的重量 → 开始执行。

#### 场景 B：练之前
> 用户到健身房，打开 App → 首页显示「今天：推日（Push A）」→ 点「开始训练」→ 进入跟练模式。

#### 场景 C：练的时候（核心场景）
> 跟练模式显示「卧推 第 1 组 / 共 4 组，目标 8 次，建议 60kg」→ 用户做完，点「完成本组」→ 自动开始 90 秒组间休息倒计时 → 用户可 ±15 秒调整或跳过 → 倒计时结束，提示音 + 语音播报「休息结束，下一组 卧推 8 次」→ 继续。
>
> **全程单手可操作**，且**屏幕不能自动熄灭**。

#### 场景 D：练之后
> 训练结束 → 显示总结（总时长 62 分钟、总容量 8,450kg、卧推创 PR）→ 数据同步到云端。

#### 场景 E：长期回顾
> 三个月后，用户在 PC 上打开 Web 端 → 看体重 7 日移动平均曲线（下降 3.2kg）→ 看深蹲估算 1RM 曲线（上升 15kg）→ 看肌群周容量柱状图（发现背部容量偏低）→ 调整计划。

## 3. 术语表

> **本节的每个词都写「本项目采用的定义」，而非通用词典释义。** 术语不统一，后面全是歧义。
> 本文档后续章节及 [METRICS.md](./METRICS.md) 中出现的领域词，以本节为准。

### 3.1 训练基本单位

| 术语 | 本项目定义 |
|---|---|
| **动作（Exercise）** | 一个可独立计量的训练动作，如「杠铃卧推」。动作库中的一条记录。 |
| **组（Set）** | 连续完成若干次动作的一个单元。训练记录的最小单位。 |
| **次（Rep）** | 组内完成一次完整动作。 |
| **组间休息（Rest）** | 两组之间的间歇时长。本项目以**秒**为单位存储。 |
| **热身组（Warmup Set）** | 为正式组做准备的轻重量组。`set_type = warmup`。 |
| **正式组（Working Set）** | 真正计入训练量的组。**默认所有统计只计正式组**。 |
| **力竭组（Failure Set）** | 做到无法再完成一次标准动作的组。`set_type = failure`。 |
| **递减组（Drop Set）** | 一组做到力竭后立即减重继续做。`set_type = drop`。 |

### 3.2 强度与计量

| 术语 | 本项目定义 |
|---|---|
| **1RM** | 只能完成 1 次的最大重量。**实测 1RM 有受伤风险，本项目不要求用户实测。** |
| **估算 1RM（e1RM）** | 由正式组的重量和次数反推的 1RM 估计值。本项目采用 **Epley 公式：`e1RM = w × (1 + r/30)`**，仅当 `r ≤ 12` 时参与计算。用于把不同重量×次数的组换算成可比的力量指标。 |
| **%1RM** | 训练重量占 1RM 的百分比。表现强度的指标。 |
| **RPE** | 主观用力程度，1–10 分。本项目采用常见的力量训练标度：RPE 8 表示「还能再做 2 次」。 |
| **RIR** | 剩余次数（Reps In Reserve）。`RIR = 10 − RPE`。与 RPE 二选一即可，本项目**存储 RPE**。 |
| **计量类型（metric_type）** | 动作的计量方式判别器。见 3.4。 |

### 3.3 训练量与强度

| 术语 | 本项目定义 |
|---|---|
| **训练容量（Volume）** | **本项目口径：仅统计正式组，`Σ(重量 × 次数)`。** 自重动作按 `Σ次数` 单独统计，不与负重动作混算。热身组**不计入**。口径必须全局统一，否则所有趋势图失真。 |
| **强度（Intensity）** | 本项目指 `平均 %1RM` 或 `平均 RPE`，用于与容量搭配解读。**容量涨 ≠ 进步**，可能只是休息变长、强度下降。 |
| **渐进超负荷** | 逐步增加重量、次数或组数以持续制造训练刺激。本项目的核心追踪目标。 |
| **deload** | 主动降低强度/容量的恢复周（通常 −40% 左右）。周期化计划的一部分，**不算作未完成计划**。 |
| **周期化（Periodization）** | 把长期计划划分为若干周，每周强度不同（递增或波动）。 |

### 3.4 计量类型（metric_type）

一个动作的计量方式，决定 `SetRecord` 上哪几个字段有意义。

| metric_type | 有意义的字段 | 举例 |
|---|---|---|
| `weight_reps` | `weight`, `reps` | 杠铃卧推、哑铃弯举 |
| `reps_only` | `reps` | 引体向上、俯卧撑 |
| `duration` | `duration_sec` | 平板支撑、死吊 |
| `distance_duration` | `distance_m`, `duration_sec` | 跑步、划船机 |

> **设计决策**：`SetRecord` 同时持有 `weight / reps / duration_sec / distance_m` 四个**可空**列，由 `Exercise.metric_type` 决定哪个有意义。
> **不用 EAV**（「取最近 10 次最佳组」这类查询会变成噩梦），也**不为每种类型建表**（JOIN 爆炸）。新增计量方式（如负重引体）只需加列。

### 3.5 计划与执行

| 术语 | 本项目定义 |
|---|---|
| **计划（Program）** | 一个长期训练安排，如「8 周增肌计划」。含总周数、每周频率、训练日结构。 |
| **训练日模板（DayTemplate）** | 计划中的一个训练日结构，如「推日 A」。含若干处方动作。 |
| **处方（PrescribedExercise）** | 训练日模板中的一个动作及其目标：目标组数、次数区间、目标重量、组间休息。 |
| **训练会话（Session / WorkoutSession）** | **某天实际执行的一次训练**。由训练日模板生成，但**独立于模板**。 |
| **组记录（SetRecord）** | 实际完成的某一组。属于某个训练会话。 |
| **跟练模式** | 按计划顺序逐动作、逐组引导用户执行，并管理组间休息计时的界面模式。 |
| **快照（Snapshot）** | 会话创建时对处方值的**深拷贝**。见 6.3 不变量。 |

### 3.6 进度指标

| 术语 | 本项目定义 |
|---|---|
| **出勤率** | `完成场次 / 计划场次`。**只看去没去，不看练得对不对**。反映习惯。 |
| **符合率** | `Σ min(实际完成, 计划目标) / Σ 计划目标`，**仅统计 exercise_id 匹配的组**，分子做 clamp 防止超 100%。反映执行度。 |
| **PR（个人纪录）** | 某动作在重量、次数或估算 1RM 上的历史最好成绩。 |

> **设计决策**：出勤率与符合率**必须是两个指标**。合成一个会被「练了但没按计划」污染——用户临时改动作、加组、减重量，在出勤率里算成功，在符合率里算偏差，但**都不该算失败**。临场调整是正常训练行为。

## 4. 范围与非目标

> **明确写出「不做什么」和理由。** 没有边界的需求文档等于没有需求文档。

### 4.1 V1 明确不做

| 不做 | 理由 | 未来触发条件 |
|---|---|---|
| 社交 / 排行榜 / 动态 | 个人工具，无社交需求；且引入内容审核负担 | 有 ≥50 名活跃用户时重新评估 |
| 饮食 / 热量 / 营养素库 | 是另一个独立领域（食物数据库体量极大），与训练记录无强耦合 | 用户明确需要「吃练一体」时 |
| 问卷式自动生成计划 | 规则引擎调参成本高，且生成的计划质量难以验证 | 内置模板库被用尽且用户主动要求时 |
| AI 生成 / 调整计划 | 同上，且难以解释「为什么这么安排」 | 不设触发条件 |
| 视频动作识别 / 计数 | 需要 CV 模型与大量标注数据，与后端岗定位无关 | 不设触发条件 |
| 可穿戴设备深度集成 | 各厂商 SDK 割裂，国内数据开放度低 | 有统一开放平台时 |
| 教练端 / 学员管理 | 面向个人用户，不是 SaaS | 不设触发条件 |
| 课程 / 教学视频 | 本项目是**记录工具**，不是教学平台 | 不设触发条件 |
| 离线冲突自动合并（CRDT） | 单用户多设备并发编辑同一会话的概率极低 | 出现真实冲突投诉时 |

### 4.2 V1 不做但预留

| 项 | 预留方式 |
|---|---|
| 对象存储（OSS） | 体态照片 V1 存本地磁盘，但存储层抽象为接口，换 OSS 不改业务代码 |
| Redis 缓存 | 不引入。JWT 无状态 + MySQL 存 refresh token 足够。指标查询先走 MySQL 索引优化 |
| 第三方登录 | 用户表预留 `provider` / `provider_user_id` 字段，V1 只实现 `local` |

## 5. 技术方案总览

### 5.1 整体架构

```
┌─────────────────┐        ┌─────────────────┐
│  Flutter App    │        │   Vue 3 Web     │
│  (iOS/Android)  │        │   (PC 浏览器)    │
└────────┬────────┘        └────────┬────────┘
         │                          │
         │    同一套 REST API        │
         └────────────┬─────────────┘
                      │ HTTPS / JSON
              ┌───────▼────────┐
              │  Spring Boot 3 │
              │  ─────────────  │
              │  Controller     │
              │  Service        │
              │  Mapper         │
              └───────┬────────┘
                      │ JDBC
              ┌───────▼────────┐
              │   MySQL 8      │
              └────────────────┘
                      │
              ┌───────▼────────┐
              │  本地文件存储    │
              │  (体态照片)      │
              └────────────────┘
```

### 5.2 技术选型

| 层 | 选型 | 理由 |
|---|---|---|
| 后端框架 | Spring Boot 3.x | JDK 17 满足要求；生态成熟 |
| 持久层 | MyBatis-Plus | 已有使用经验；复杂聚合查询比 JPA 更可控 |
| 数据库 | MySQL 8.0 | 本机已装并运行 |
| 鉴权 | Spring Security + JWT | 无状态，双端友好 |
| 数据库迁移 | Flyway | 版本化 DDL，比手写 SQL 脚本专业 |
| 接口文档 | springdoc-openapi | 自动生成 Swagger UI，可直接演示 |
| 客户端 | Flutter 3.x + Dart 3 | 一套代码出双平台 |
| 客户端状态管理 | Riverpod | 编译期安全，测试友好 |
| 客户端本地存储 | drift (SQLite) | 离线优先的落地基础 |
| Web 端 | Vue 3 + Vite + TypeScript | 国内 Java 岗最常见组合 |
| Web UI 组件 | Element Plus | 后台型界面开发效率高 |
| Web 图表 | ECharts | 国内标准，图表类型全 |

### 5.3 双端共用一套 API

**核心约束**：Flutter App 与 Vue Web **访问完全相同的 REST API**，不存在端专属接口。

含义：
- 接口设计以**领域资源**为中心（`/api/v1/sessions`），不以**页面**为中心（`/api/v1/today-page`）。
- 分页、排序、筛选参数在两端语义一致。
- Web 端需要而 App 端不需要的数据（如长周期聚合），通过**同一接口的不同查询参数**获得，不新建接口。

### 5.4 离线优先策略

**背景**：健身房信号差，跟练时每记一组都打接口，体验会崩。

**分级**：

| 能力 | 离线可用性 | 说明 |
|---|---|---|
| 跟练记录 | **完全离线** | 写本地 SQLite，训练结束后批量同步 |
| 查看今日计划 | **完全离线** | 提前缓存 |
| 查看历史记录 | 只读离线 | 缓存最近 N 次 |
| 身体数据录入 | 离线可写 | 进同步队列 |
| 图表 / 统计 | 需要在线 | 聚合计算在后端 |
| 账号相关 | 需要在线 | — |

**同步策略**：会话结束时批量上传。客户端为每条记录生成 UUID 作为幂等键，后端按 UUID 去重，重复上传不产生脏数据。

### 5.5 不引入 Redis 的理由

JWT 是无状态的，不需要 session 存储；refresh token 存 MySQL 即可。指标聚合查询先用索引优化，V1 的数据量（单用户数千条组记录）远达不到需要缓存的规模。**为了用而用中间件是负分**——面试官会问「为什么需要 Redis」，答不上来不如不用。

## 6. 领域模型

> 完整字段定义见实现阶段的建表 SQL。本节定义**实体关系与关键不变量**。

### 6.1 实体清单

| 实体 | 说明 |
|---|---|
| `User` | 用户账号与个人资料 |
| `Exercise` | 动作库（内置 + 用户自定义） |
| `Program` | 训练计划（含版本号） |
| `WeekTemplate` | 计划的周结构（强度修饰） |
| `DayTemplate` | 训练日模板 |
| `PrescribedExercise` | 训练日中的处方动作 |
| `WorkoutSession` | 实际执行的训练会话 |
| `SessionExercise` | 会话中的动作（含处方快照） |
| `SetRecord` | 组记录 |
| `BodyMetric` | 身体指标（长表） |
| `PersonalRecord` | 个人纪录 |
| `ProgressPhoto` | 体态照片元数据 |

### 6.2 关系主线

```
Program ──< WeekTemplate ──< DayTemplate ──< PrescribedExercise >── Exercise
   │                                              │
   │ 展开（创建会话时深拷贝为快照）                  │
   ▼                                              ▼
WorkoutSession ──< SessionExercise ──< SetRecord >── Exercise
                                            │
                                            └──> PersonalRecord（触发更新）
```

**单向流动，永不回写。**

### 6.3 关键不变量

> 这三条是数据模型的地基，违反任何一条都会导致历史数据错误。

**不变量 1：历史会话不受计划变更影响。**
`WorkoutSession` 创建时，把 `PrescribedExercise` 的处方值**深拷贝**到 `SessionExercise`。此后用户修改计划，已创建的会话及其快照**不变**。

- 反例：若会话只存 `prescribed_exercise_id` 外键，用户第 5 周改了训练日的动作，前 4 周的历史会显示成改后的样子。
- 用户想「以后都按这个来」时，走**显式 promote**：生成计划新版本，不回写历史。

**不变量 2：计划的任何改动产生新版本号。**
`Program` 有 `version` 字段。已开始的会话锁定其创建时的版本。修改一个进行中的计划 → 新版本生效于未来会话，旧版本的历史不受影响。

**不变量 3：组记录永不回写模板。**
`SetRecord` 只属于 `WorkoutSession`。用户临场改重量、加组、换动作，**只影响本次会话**，不会污染计划模板。

### 6.4 周期化的建模

**问题**：8 周 × 每周 3 练 = 24 个训练日。手写 24 个 `DayTemplate` 不可维护。

**方案**：结构 × 强度修饰分离。

- `DayTemplate` 定义**结构**：推日 A / 拉日 A / 腿日 A（共 3 个）
- `WeekTemplate` 定义**强度修饰**：第 1–4 周 +0%、第 5–7 周 +5%、第 8 周 deload −40%（共 8 个）

**处方值在会话创建时展开计算**，结果写入快照。模板只存 3 + 8 = 11 条记录，而非 24 条。

### 6.5 计量多态

见 3.4。`SetRecord` 用**宽字段 + 判别器**：

```sql
-- 示意，非最终 DDL
CREATE TABLE set_record (
  id            BIGINT PRIMARY KEY,
  session_exercise_id BIGINT NOT NULL,
  set_index     INT NOT NULL,
  set_type      ENUM('warmup','working','failure','drop') NOT NULL DEFAULT 'working',
  weight        DECIMAL(6,2)  NULL,   -- metric_type = weight_reps
  reps          SMALLINT      NULL,   -- weight_reps / reps_only
  duration_sec  INT           NULL,   -- duration / distance_duration
  distance_m    DECIMAL(8,2)  NULL,   -- distance_duration
  rpe           DECIMAL(3,1)  NULL,
  rest_actual_sec INT         NULL,
  completed_at  DATETIME      NOT NULL
);
```

**volume 是派生值**，不入库（或入库时绑定口径版本号），避免口径变更后历史数据无法重算。

## 8. 非功能需求

### 8.1 离线可用性

分级见 5.4。**核心约束：跟练全程必须完全离线可用**，联网只影响同步时机，不影响记录。

### 8.2 计时精度

| 场景 | 要求 |
|---|---|
| 前台正常计时 | 误差 ≤ 0.5 秒 |
| 切后台 5 分钟后返回 | 剩余时间误差 ≤ 1 秒 |
| 锁屏 10 分钟后解锁 | 剩余时间误差 ≤ 1 秒 |
| 系统时间被手动修改 | 不产生负计时或跳跃 |

实现约束见 [TIMER-SPEC.md](./TIMER-SPEC.md)：**只存绝对时间戳，不存剩余秒数**。

### 8.3 性能

| 指标 | 目标 |
|---|---|
| API P95 响应时间 | ≤ 300ms（不含文件上传） |
| 列表接口分页 | 默认 20 条，最大 100 条 |
| 首页加载（含今日计划） | ≤ 1.5 秒 |
| 跟练界面组切换 | 无感知延迟（本地读写） |
| 图表查询（一年数据） | ≤ 1 秒 |

### 8.4 安全与隐私

| 项 | 要求 |
|---|---|
| 密码存储 | BCrypt，cost ≥ 10 |
| Token | access token 短期（≤ 1 小时），refresh token 长期可撤销 |
| 越权防护 | **所有资源查询强制带 `user_id` 条件**，禁止仅凭 ID 查询 |
| 体态照片 | 仅本人可访问；文件名使用 UUID，不可枚举 |
| 传输 | 生产环境强制 HTTPS |
| 敏感配置 | 数据库密码等写入 `application-dev.yml` 并加入 `.gitignore` |

### 8.5 可测试性

| 项 | 目标 |
|---|---|
| 核心业务逻辑单元测试覆盖 | Service 层关键路径（计划展开、容量计算、PR 判定） |
| 接口测试 | 主要 REST 接口有集成测试 |
| 测试数据库 | 独立的 `gym_log_test` 库，不污染开发数据 |

### 8.6 可维护性

| 项 | 要求 |
|---|---|
| 数据库变更 | 全部通过 Flyway 迁移脚本，禁止手工改表 |
| 接口版本 | URL 前缀 `/api/v1/` |
| 接口文档 | springdoc 自动生成，与代码同步 |

## 9. 验收标准

> 每条都必须能用「是 / 否」判定。**不接受「体验流畅」这类不可测表述。**

### 9.1 跟练（M4）

| 编号 | 验收标准 |
|---|---|
| AC-4-1 | 跟练中锁屏 5 分钟，解锁后剩余休息时间误差 **≤ 1 秒** |
| AC-4-2 | 跟练中杀掉 App 进程并重开，能恢复到中断前的动作与组数 |
| AC-4-3 | 飞行模式下完成一整场训练，落地后联网同步成功，无数据丢失 |
| AC-4-4 | 跟练全程**屏幕不自动熄灭** |
| AC-4-5 | 组间休息倒计时结束时，**有可听见的提示音**（静音模式下震动或通知代替） |
| AC-4-6 | 删除组的操作需要二次确认，误触不会丢数据 |
| AC-4-7 | 主操作按钮可单手拇指触达，按钮高度 ≥ 64dp |

### 9.2 数据一致性（M3 / M5）

| 编号 | 验收标准 |
|---|---|
| AC-3-1 | 修改已开始计划的第 3 周动作，**前 2 周的历史记录显示完全不变** |
| AC-3-2 | 修改计划后，计划 `version` 递增，未来会话使用新版本 |
| AC-3-3 | 临场把某组重量从 60kg 改成 65kg，**计划模板中的目标重量不变** |
| AC-5-1 | 同一会话重复上传 3 次，数据库中不产生重复记录 |

### 9.3 指标计算（M7）

| 编号 | 验收标准 |
|---|---|
| AC-7-1 | 体积计算排除 `set_type = warmup` 的组 |
| AC-7-2 | 体重数据点不足 3 天时，**不显示移动平均线** |
| AC-7-3 | 某动作某次训练的所有组 `reps > 12` 时，该次不参与估算 1RM 曲线 |
| AC-7-4 | 估算 1RM 取每次训练的**最佳组**，而非全部组平均 |
| AC-7-5 | 符合率的计算结果**不超过 100%** |
| AC-7-6 | 添加一条 5kg×12 和一条 20kg×3 的记录，估算 1RM 分别为 7kg 和 22kg |

### 9.4 接口与架构（M1）

| 编号 | 验收标准 |
|---|---|
| AC-1-1 | 用户 A 无法通过修改 URL 中的 ID 访问用户 B 的任何数据 |
| AC-1-2 | access token 过期后，客户端自动用 refresh token 续期，用户无感知 |
| AC-1-3 | 登出后，原 refresh token 立即失效 |
| AC-1-4 | Flutter 端与 Web 端调用的接口路径完全一致（无端专属接口） |

### 9.5 环境（Phase 0）

| 编号 | 验收标准 |
|---|---|
| AC-0-1 | `flutter doctor` 的 Android toolchain 显示 ✓ |
| AC-0-2 | `adb devices` 能列出真机 |
| AC-0-3 | `flutter run` 能在真机上跑起 demo |
| AC-0-4 | 在**新开的**终端里 `ANDROID_HOME` 可读（不是只在当前会话） |
