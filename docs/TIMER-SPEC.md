# gym-log 跟练计时规格

> 本文档定义 [REQUIREMENTS.md](./REQUIREMENTS.md) 第 7 节 **M4 今日训练与跟练** 的实现规格。
>
> 跟练是本项目**最容易出 bug 的功能**：它涉及计时、后台运行、本地持久化、跨平台能力差异四个易错点。本文档把这些约束写死。

---

## 0. 第一原则

> **计时的唯一真相是绝对时间戳（epoch ms）。**
> **绝不存储「剩余秒数」，绝不用累加 tick 计算时间。**

**为什么**：

移动操作系统会在 App 切到后台时冻结或节流定时器。假设实现是「每秒把剩余秒数减 1」：

```
前台：remaining = 90 → tick → 89 → tick → 88 ...
用户切后台（tick 被冻结）
30 秒后回到前台
实际的 remaining 应该是 58，但变量还是 88
→ 误差 30 秒，且会一直累积
```

如果存的是「休息结束的绝对时刻」（`restDeadlineAt = 现在 + 90秒`），那么无论中断多久，回到前台时只要算 `restDeadlineAt − now` 就是准确值。**中断 30 秒不漂移，中断 30 分钟也不漂移。**

这条原则是后面所有设计的基础。

## 1. 状态机

### 1.1 状态定义

| 状态 | 含义 | 屏幕上显示 |
|---|---|---|
| `idle` | 未开始 | 今日训练卡片 |
| `preparing` | 已开始，正在做本组之前的准备（可选，用户手动进入） | 本组目标 + 「开始本组」按钮 |
| `exercising` | 正在做当前组 | 目标次数、建议重量、已用时间（正计时） |
| `resting` | 组间休息中 | 倒计时、±15 秒、跳过 |
| `exercise_done` | 当前动作所有组完成，动作间过渡 | 「下一个动作：XX」+ 继续按钮 |
| `session_done` | 本次训练所有动作完成 | 训练总结 |
| `paused` | 用户主动暂停（休息中） | 倒计时冻结 + 继续按钮 |

### 1.2 状态转移

```
                    ┌──────────┐
                    │   idle   │
                    └────┬─────┘
                         │ 开始训练
                         ▼
                  ┌─────────────┐
        ┌────────►│  preparing  │◄────────┐
        │         └──────┬──────┘         │
        │                │ 开始本组        │ 跳过休息
        │                ▼                │
        │         ┌─────────────┐         │
        │         │ exercising  │         │
        │         └──────┬──────┘         │
        │                │ 完成本组        │
        │                ▼                │
        │         ┌─────────────┐         │
        │         │  setDone    │─────────┤
        │         └──────┬──────┘         │
        │                │                │
        │     还有组 ────┴──── 无更多组     │
        │         │              │         │
        │         ▼              ▼         │
        │   ┌──────────┐  ┌──────────────┐ │
        └───│ resting  │  │exercise_done │─┘
            └────┬─────┘  └──────┬───────┘
                 │               │ 还有动作
                 │               └──────► preparing（下一个动作）
                 │ 无更多动作
                 ▼
            ┌──────────────┐
            │ session_done │
            └──────────────┘
```

### 1.3 转移条件与副作用

| 从 | 到 | 触发 | 副作用 |
|---|---|---|---|
| `idle` | `preparing` | 用户点「开始训练」 | 创建 `WorkoutSession`，深拷贝处方快照，启动 Wake Lock |
| `preparing` | `exercising` | 点「开始本组」 | 记录 `phaseStartedAt = now` |
| `exercising` | `setDone` | 点「完成本组」（或耳机线控） | **立即落盘 SetRecord**，判定 PR |
| `setDone` | `resting` | 自动（还有组） | `restDeadlineAt = now + 该动作的 rest_sec` |
| `setDone` | `exercise_done` | 自动（无更多组） | — |
| `resting` | `preparing` | 倒计时归零 / 点「跳过」 | 记录 `rest_actual_sec`，提示音 + 语音播报 |
| `resting` | `paused` | 点「暂停」 | 记录 `pausedAt`，冻结倒计时 |
| `paused` | `resting` | 点「继续」 | `restDeadlineAt += (now − pausedAt)` |
| `exercise_done` | `preparing` | 点「下一个动作」/ 自动 | 切到下一个 `SessionExercise` |
| `exercise_done` | `session_done` | 无更多动作 | 释放 Wake Lock，触发同步 |
| 任意 | `session_done` | 用户点「结束训练」 | **二次确认**；未完成的组标记为 `skipped` |

### 1.4 关键设计决策

**决策 1：`setDone` 是一个真实状态，不是瞬时事件。**

「完成本组」和「进入休息」之间要有明确的状态。否则用户在落盘完成的瞬间杀掉 App，恢复时会不知道那一组到底算不算。有了 `setDone`，恢复逻辑可以判断「已落盘，未进入休息」。

**决策 2：`paused` 只允许在 `resting` 时进入。**

训练中是正计时，暂停没有意义（用户不会中途暂停深蹲）。休息倒计时暂停才有意义（接电话、去洗手间）。

**决策 3：暂停通过平移 `restDeadlineAt` 实现，不引入 `remaining` 变量。**

```
暂停：pausedAt = now
继续：restDeadlineAt = restDeadlineAt + (now − pausedAt)
```

这样「剩余时间」永远只有 `restDeadlineAt − now` 一个来源，不存在两个真相。

## 2. 持久化

### 2.1 存储结构

跟练状态写入本地 SQLite（drift），**每次状态转移立即写入**。

```dart
// 示意结构，非最终代码
class ActiveSession {
  String sessionId;          // UUID，同时是服务端幂等键
  int currentExerciseIndex;  // 当前是第几个动作
  int currentSetIndex;       // 当前是第几组
  String phase;              // 状态机当前状态
  int? phaseStartedAt;       // epoch ms，进入当前状态的时刻
  int? restDeadlineAt;       // epoch ms，休息结束的绝对时刻
  int? pausedAt;             // epoch ms，暂停时刻（仅 paused 状态有值）
  int restDurationSec;       // 本次休息的总时长（用于计算进度百分比）
  bool wakeLockActive;
  int updatedAt;             // epoch ms，用于冲突检测
}
```

**全部时间字段是 epoch ms（`int`），没有任何「剩余秒数」字段。**

### 2.2 落盘时机

| 时机 | 写什么 |
|---|---|
| 创建会话 | 完整状态 |
| 每次状态转移 | 完整状态（UPSERT） |
| 完成一组 | `SetRecord` + 状态（**同一事务**） |
| 休息中每 30 秒 | `updatedAt` 心跳（用于崩溃检测） |
| 训练结束 | 标记 `completed`，清理本地活动状态 |

**「同一事务」很重要**：如果 `SetRecord` 写成功但状态没更新，恢复时用户会看到那一组没打勾，可能重复记录。

### 2.3 恢复流程

App 启动时检查是否存在未完成的活动会话：

```
如果存在 ActiveSession 且 phase != 'session_done'：

  1. 计算时间跳变
     elapsed = now − updatedAt

  2. 按 phase 分支：
     ├─ exercising / preparing
     │    → 直接恢复，正计时基于 phaseStartedAt 计算
     │
     ├─ resting
     │    → remaining = restDeadlineAt − now
     │      ├─ remaining > 0  → 恢复到休息中，剩余 remaining
     │      └─ remaining ≤ 0  → 休息早已结束
     │           显示「休息已结束 3 分 12 秒」
     │           不自动进入下一组（用户可能已经忘了）
     │           让用户点「开始下一组」
     │
     ├─ setDone
     │    → 组已落盘，恢复时自动推进到 resting 或 exercise_done
     │
     └─ paused
          → 保持暂停，等用户点继续
             （不按 elapsed 平移，因为用户是主动暂停的）

  3. 弹窗询问：「检测到未完成的训练（卧推 第 3 组），是否继续？」
     ├─ 继续 → 恢复到上述状态
     └─ 放弃 → 标记会话为 abandoned，保留已记录的组
```

**注意 `resting` 超时的情况**：不要自动跳到下一组。用户可能已经练完走了，或者练完那组忘了点。自动跳会导致数据错位。**让用户确认。**

## 3. Flutter 平台能力矩阵

### 3.1 能力对照

| 能力 | Android | iOS | 实现方案 |
|---|---|---|---|
| **屏幕常亮** | ✅ `FLAG_KEEP_SCREEN_ON` | ✅ `idleTimerDisabled` | `wakelock_plus` |
| **震动** | ✅ 任意时长 | ⚠️ **仅 Haptic Feedback**，无任意时长震动 | `vibration` + `HapticFeedback` 降级 |
| **提示音** | ✅ | ✅ | `audioplayers` 播放本地音频 |
| **语音播报** | ✅ | ✅ | `flutter_tts` |
| **后台通知** | ✅ 前台服务 + 通知 | ⚠️ 需权限，后台执行受限 | `flutter_local_notifications` |
| **后台持续计时** | ⚠️ 需前台服务 | ❌ **不允许长时间后台执行** | **不依赖后台执行**（见第 0 节） |
| **耳机线控** | ✅ MediaSession | ✅ | 见 3.4 |

### 3.2 关键约束：iOS 震动

**iOS 不向第三方 App 开放任意时长的震动控制。** 只能触发系统的 Haptic Feedback（Tap / Impact 等固定模式）。

**因此需求中不能写「iOS 上震动提醒」**，必须写成「iOS 上使用触觉反馈」。这是真实的平台限制，不是实现偷懒。

### 3.3 提示通道可靠性排序

| 优先级 | 通道 | 可靠性 | 是否需要资源/权限 |
|---|---|---|---|
| 1 | **提示音**（本地音频） | 高 | 无 |
| 2 | **语音播报**（TTS） | 中（需初始化） | 无 |
| 3 | **震动 / 触觉** | Android 高 / iOS 低 | Android 需权限 |
| 4 | 本地通知 | 高 | 需通知权限 |

**主通道选提示音**：不需要任何权限，不需要网络，不需要额外资源文件（可用代码合成音调），跨平台一致。

**默认组合**：提示音 + 震动（Android）。**语音播报默认关闭**，因为健身房环境嘈杂，且 TTS 在部分设备上初始化慢。

### 3.4 音频提示设计

计时提示音不能只是一个「叮」。需要**分频编码**，让用户不看屏幕也能判断状态：

| 时刻 | 声音 | 含义 |
|---|---|---|
| 剩余 3 秒 | 三声短促中音（每 500ms 一声） | 准备 |
| 归零 | 一声长高音 | 开始下一组 |
| 剩余 30 秒 | 一声短低音（可选） | 心里有数 |

这样用户闭着眼也能知道还剩多久。

**耳机线控 / 媒体键**：通过 `audio_service` 或平台通道把「播放/暂停键」映射为「完成本组」。这是力量训练的高价值细节——用户在卧推凳上不方便掏手机。

### 3.5 权限清单

| 权限 | 平台 | 用途 | 时机 |
|---|---|---|---|
| `VIBRATE` | Android | 震动提示 | 首次跟练时申请 |
| `POST_NOTIFICATIONS` | Android 13+ | 后台提醒 | 首次跟练时申请 |
| `FOREGROUND_SERVICE` | Android | 长时间保持计时 | 跟练开始时 |
| 通知权限 | iOS | 后台提醒 | 首次跟练时申请 |

**申请时机**：在用户第一次点「开始训练」时申请，而不是 App 启动时。启动时申请权限会被大量拒绝。

## 4. 边界情况

### 4.1 时间跳变

| 情况 | 检测 | 处理 |
|---|---|---|
| **用户手动改系统时间** | `now` 与上次心跳的差值异常（如突然 −3600 秒） | 展示用**单调钟**（`Stopwatch` / `performance.now()`），持久化用 `Date.now()`，两者交叉校验。检测到跳变时以单调钟为准 |
| **时区变更** | `now` 跳变且偏移量接近整小时 | 影响的是显示格式，不影响 epoch ms 计算 |
| **NTP 校时** | 小幅跳变（< 5 秒） | 忽略 |
| **设备重启** | 内存状态丢失 | 从 SQLite 恢复（第 2.3 节） |

**实现要点**：

```dart
// 展示：用单调钟，不受系统时间影响
final stopwatch = Stopwatch()..start();

// 持久化：用墙钟，因为要跨进程重启
final deadline = DateTime.now().millisecondsSinceEpoch + 90000;

// 校验：如果两者算出的经过时间差异 > 2 秒，判定系统时间被改
```

### 4.2 中断

| 情况 | 处理 |
|---|---|
| **来电** | App 进入后台，计时继续（基于 epoch ms 不受影响）。回到前台自动恢复显示 |
| **闹钟 / 其他通知** | 同上 |
| **用户切到音乐 App** | 同上 |
| **系统杀后台** | 从 SQLite 恢复 |
| **App 崩溃** | 同上，且因为每次转移都落盘，最多丢失当前组的输入 |

### 4.3 多设备并发

同一用户在两台设备上打开同一个未完成的会话：

| 检测 | 处理 |
|---|---|
| `updatedAt` 冲突（服务端版本 > 本地版本） | **乐观锁**：上传时带版本号，冲突则拒绝并提示用户「该训练已在其他设备更新」 |
| 两端都产生了新数据 | **不自动合并**。让用户选择保留哪一份 |

**概率评估**：单用户在两台设备上同时跟练同一场次的可能性极低。V1 只做**检测并提示**，不做自动合并（CRDT 复杂度不值得）。

### 4.4 数据一致性

| 风险 | 防护 |
|---|---|
| 重复上传同一会话 | 客户端生成 UUID，服务端按 UUID 唯一索引去重 |
| 组记录重复 | `(session_id, exercise_id, set_index)` 唯一约束 |
| 部分上传失败 | 同步队列重试，指数退避，最多 5 次后转人工提示 |
| 本地与服务端数据冲突 | 以服务端为准，本地保留副本供用户导出 |

## 5. 交互规格

### 5.1 尺寸与位置

| 元素 | 规格 | 理由 |
|---|---|---|
| 主操作按钮 | 高度 **≥ 64dp**，宽度占满 | 戴手套也能点中 |
| 主按钮位置 | **屏幕下半部**（底部 1/3） | 拇指热区，单手可及 |
| 倒计时数字 | **≥ 72sp** | 放在架子上也能看清 |
| 重量步进器 | 大号 `−2.5 / +2.5`，中间显示当前值 | 减少键盘弹出 |
| 次数按钮 | 大号 `−1 / +1` | 同上 |

### 5.2 降噪

| 规则 | 理由 |
|---|---|
| 倒计时数字**每 10 秒才变化**（显示 `90 → 80 → 70`） | 每秒跳动造成视觉噪声，用户会一直盯着看 |
| 最后 10 秒恢复逐秒显示 | 需要精确感知 |
| 当前组的**已完成组数用圆点**表示，不用文字 | 一眼扫过 |
| 隐藏与当前操作无关的所有信息 | 跟练时只有一件事要做 |

### 5.3 误触防护

| 操作 | 防护 |
|---|---|
| 删除组 | **二次确认弹窗** |
| 结束训练 | **二次确认弹窗** |
| 跳过休息 | 视觉弱化（次要按钮样式）+ **远离主按钮** |
| 修改重量 | 5 秒内可撤销的 Toast，不弹确认框 |
| 删除动作 | 二次确认 |

> **原则：高频操作用撤销，低频破坏性操作用确认。**
> 每次改重量都弹确认框会让人发疯；而误删一组没有确认就是数据丢失。

## 7. 不做什么

| 不做 | 理由 |
|---|---|
| 后台常驻服务持续计时 | 不需要。绝对时间戳方案本身就不依赖后台执行 |
| 自动识别动作（摄像头） | 见 [REQUIREMENTS.md 第 4 节](./REQUIREMENTS.md#4-范围与非目标) |
| 超级组（两动作交替无休息） | V1 状态机复杂度会显著上升。留待 V2（见未决问题 Q5） |
| 组内实时计数（自动数次数） | 需要传感器或 CV，不在范围内 |
| 与智能手表联动控制 | 各厂商 SDK 割裂 |
