# gym-log 指标口径与图表规格

> 本文档定义 [REQUIREMENTS.md](./REQUIREMENTS.md) 第 7 节 **M7 数据可视化** 中每个指标的计算口径、公式、边界情况与图表形态。
>
> 术语以 [REQUIREMENTS.md 第 3 节](./REQUIREMENTS.md#3-术语表) 为准。

---

## 0. 总原则

### 0.1 准入标准

> **答不出「看完这张图我会改变什么行为」的图，不做。**

每新增一张图，必须先回答：
1. 这张图回答什么问题？
2. 看到什么形态时，用户会改变什么行为？
3. 如果图上是「正常」的，用户是否会感到安心？

答不出第 2 条，这张图就是装饰，不做。

### 0.2 通用约定

| 约定 | 说明 |
|---|---|
| **容量一律排除热身组** | 所有涉及 volume 的计算，`WHERE set_type != 'warmup'`。这是最容易出错的地方。 |
| **重量单位统一存 kg** | 数据库一律 kg，`lb` 仅在显示层换算。避免单位混存导致历史数据无法比较。 |
| **时间统一存 UTC** | 展示层按用户时区转换。训练跨零点时以**开始时间**归属日期。 |
| **缺失数据不插值** | 没有数据就是没有数据，不用 0 填充，也不线性插值。图上直接断开。 |

### 0.3 聚合粒度

| 粒度 | 用途 |
|---|---|
| 单组（set） | 训练详情、单动作历史表 |
| 单次训练（session） | 训练总结、单动作进展曲线取点 |
| 单周（week，周一起算） | 容量、频率、出勤率 |
| 单月 | 长期趋势的次要视图 |

> **周起点定为周一**，非周日。国内用户习惯。

### 0.4 平台适配

**本文档描述的图表规格以 PC 端（Vue + ECharts）为基准。** 手机端（Flutter + fl_chart）的端归属、设计约束与逐图差异**以 [REQUIREMENTS.md M7-B](./REQUIREMENTS.md#m7-b-平台适配手机-vs-pc) 为准**。

手机端统一适用以下三条，本文档各节不再重复：

| 约束 | 说明 |
|---|---|
| **单序列** | 不做多序列叠加。多部位/多动作的图在手机端一律改为「切换器 + 单条线」 |
| **默认 3 个月** | PC 默认 1 年 |
| **长按读数** | 替代 PC 的鼠标悬停。**缺这个，图表就只是装饰** |

**Y 轴范围的规则两端一致**：计数类（组数、次数）从 0 开始；测量类（体重、1RM、围度）不从 0 开始，取数据范围各留 10% 余量。这条不因屏幕大小而变。

## 1. 体重 / 体脂

### 1.1 定义

| 项 | 内容 |
|---|---|
| **回答的问题** | 我的体重趋势是升是降？速度合理吗？ |
| **数据来源** | `BodyMetric`，`metric_type IN ('weight','body_fat')` |
| **单位** | kg / % |

### 1.2 公式

**原始点**：每次测量的实际值。

**移动平均（主线）**：

```
MA7(d) = 最近 7 天内所有测量值的算术平均
```

**结论指标**：

```
周均值(w) = 该周所有测量值的算术平均
变化量     = 本周均值 − 上周均值
```

### 1.3 为什么必须用移动平均

**日间体重波动 1–2kg**（水分、糖原、钠摄入、肠道内容物），而**每周真实脂肪变化约 0.5kg**（对应约 500 kcal/日缺口，按 1kg 脂肪 ≈ 7700 kcal 计）。

**信噪比是 1:2 到 1:4——噪声比信号还大。** 原始日点图会呈现剧烈的锯齿，用户看到某天涨了 1.5kg 就可能做出错误决策：减餐、加有氧、怀疑计划失效。而这些波动跟脂肪毫无关系。

移动平均把噪声压下去，露出来的才是趋势。

### 1.4 图表规格

| 项 | 规格 |
|---|---|
| **图表类型** | 折线图 |
| **主序列** | 7 日移动平均线（实线，视觉权重最高） |
| **副序列** | 原始测量点（浅色小点，低透明度，作为背景） |
| **可选序列** | 28 日移动平均（虚线，用于看更长趋势） |
| **X 轴** | 时间 |
| **Y 轴** | **不从 0 开始**。体重变化幅度小，从 0 开始会把趋势压成一条平线。Y 轴范围取数据的最小/最大值各留 10% 余量。 |
| **测量条件标记** | 条件不同的点用**不同形状**区分（晨起空腹=圆点，训练后=三角，其他=方点） |
| **交互** | 点击某点显示该次测量值、测量条件、相对 7 日均值的偏差 |

### 1.5 边界情况

| 情况 | 处理 |
|---|---|
| **数据点 < 3 天** | **不显示移动平均线**，只显示原始点，并提示「数据不足，继续记录以查看趋势」 |
| 数据点 3–6 天 | 显示移动平均但标注「样本较少，仅供参考」 |
| 连续 14 天无数据 | 曲线断开，不连线跨越空档 |
| 单日多次测量 | 取该日平均值作为当天的点 |
| 测量条件混杂 | 不阻止，但在图上区分标记；统计周均值时可筛选「仅晨起空腹」 |

### 1.6 什么时候不显示

- 总数据点 < 3：只显示原始点
- 时间跨度 < 7 天：不显示 28 日均线

## 2. 围度趋势

### 2.1 定义

| 项 | 内容 |
|---|---|
| **回答的问题** | 我的体型在变吗？增肌期该长的地方长了吗？ |
| **数据来源** | `BodyMetric`，`metric_type = 'circumference'`，按 `site` 区分部位 |
| **部位** | 胸、腰、臀、左/右臂、左/右大腿、左/右小腿 |

### 2.2 公式

**各部位独立计算**，不合并。变化量 = 本次 − 上次。

**左右差值**（仅四肢）：

```
不对称度 = |左侧 − 右侧| / max(左侧, 右侧) × 100%
```

### 2.3 为什么围度比体重更有价值

增肌期体重上升时，分不清是肌肉还是脂肪。腰围不涨而臂围涨，才是干净的增肌。减脂期同理——腰围下降比体重下降更能说明问题。

**围度是体重的解释变量，不是替代品。** 两者要放在一起看。

### 2.4 图表规格

| 项 | 规格 |
|---|---|
| **图表类型** | 多序列折线图（小倍数图 / small multiples 优先） |
| **布局** | **每个部位一个小图**，纵向排列，共享 X 轴。不要把所有部位挤在一张图上——7 个部位 7 条线无法辨认 |
| **Y 轴** | 各部位独立缩放，不从 0 开始 |
| **参考线** | 无（围度没有通用标准值，个体差异极大） |
| **左右对比** | 四肢部位在同一小图内画左右两条线，便于发现不对称 |

### 2.5 边界情况

| 情况 | 处理 |
|---|---|
| 测量频率低（月度） | 点之间用直线连接，标注「测量间隔较长」 |
| 只测了部分部位 | 只显示有数据的部位的小图，不显示空图 |
| 左右不对称度 > 10% | 图上标注提示（可能是测量误差，也可能是真实不对称） |

### 2.6 什么时候不显示

- 某部位数据点 < 2：不显示该部位小图

## 3. 力量进展（估算 1RM 曲线）

### 3.1 定义

| 项 | 内容 |
|---|---|
| **回答的问题** | 我这个动作变强了吗？变强了多少？ |
| **数据来源** | `SetRecord` + `Exercise.metric_type = 'weight_reps'` |
| **单位** | kg |

### 3.2 公式

**Epley 公式**：

```
e1RM = w × (1 + r / 30)
```

**取点规则（关键）**：每次训练，取该动作**所有正式组中 e1RM 最大的那一组**作为本次训练的代表值。

```
session_e1RM(session, exercise) = MAX( w_i × (1 + r_i/30) )
                                  对所有 set_type != 'warmup' 的组
```

**体重归一化**（减脂期必需）：

```
relative_1RM = e1RM / 体重(kg)
```

### 3.3 三个必须遵守的规则

**规则 1：只用估算 1RM，不用原始重量。**

原始重量不可比。`5kg × 12` 和 `20kg × 3` 哪个更强？看重量是 20kg 大，看容量是 60kg vs 60kg 打平，但按 Epley 分别是 **7kg** 和 **22kg**。不做换算，力量进展曲线就是一堆噪声。

**规则 2：`r > 12` 的组不参与估算。**

Epley 在高次数区间**严重高估**。20 次力竭组的真实 1RM 远低于公式给出值。超过 12 次的组排除，避免曲线被高次数组虚抬。

**规则 3：取最佳组，不取平均。**

如果用全部组的 e1RM 平均，热身组残留、递减组、疲劳组会把值拉低，曲线会**低估**真实力量，且受当天组数安排影响。最佳组最接近当天的真实能力上限。

### 3.4 图表规格

| 项 | 规格 |
|---|---|
| **图表类型** | 折线图 + 散点 |
| **主序列** | 每次训练的最佳组 e1RM（折线连接） |
| **副序列** | 该次的全部组（浅色散点，展示当天的离散程度） |
| **X 轴** | 时间 |
| **Y 轴** | kg，不从 0 开始 |
| **参考线** | 历史最高 e1RM（虚线） |
| **切换** | 绝对 e1RM ↔ 体重归一化 1RM |
| **默认范围** | 最近 6 个月，可切 3 个月 / 1 年 / 全部 |

### 3.5 边界情况

| 情况 | 处理 |
|---|---|
| 本次训练所有组 `reps > 12` | **该次不参与曲线**，但训练记录正常保存 |
| 单次训练只有热身组 | 不取点 |
| 动作换了（如卧推换上斜卧推） | 不同 `exercise_id` 分开画，不合并 |
| 中途换过器械（杠铃→哑铃） | 提示用户「该动作存在器械变更」，但同 `exercise_id` 仍画一条线 |
| 数据点 < 2 | 只显示散点，不连线 |

### 3.6 什么时候不显示

- `metric_type != 'weight_reps'` 的动作：**不显示此图**（自重、时长类动作没有 e1RM 概念）
- 数据点 = 1：只显示单点数值，不画曲线

## 4. 训练容量与肌群组数

> **本节包含两个独立指标，它们不可互相替代。** 混用会导致错误的训练决策——这是本节存在的全部理由。

### 4.0 两个指标，各司其职

| 指标 | 定义 | 单位 | 回答的问题 | 用在哪 |
|---|---|---|---|---|
| **训练容量** | `Σ(重量 × 次数)`，仅正式组 | kg | 我的总训练负荷在涨吗？ | 训练总结、单动作进展、整体负荷趋势 |
| **肌群组数** | 各肌群的正式组数 | 组 | 我各肌群练得均衡吗？ | 肌群周对比图 |

**为什么不能只留一个**：

- **只用容量 → 肌群图废掉**。肌群之间重量不可比：卧推 80kg×8（640）和侧平举 10kg×15（150）差 4 倍。腿和背会主导图表，手臂和肩被压成看不见的线。
- **只用组数 → 看不出负荷变化**。同样是 15 组，用 60kg 做和用 80kg 做，训练刺激完全不同。组数相同但负荷翻倍，是实打实的进步，只看组数会漏掉。

**运动科学文献里讨论「每周 10–20 组」用的单位是组数**，不是容量。所以肌群对比图必须用组数，这不是妥协，是正确做法。

---

### 4.1 训练容量（`Σ(重量×次数)`）

#### 定义

| 项 | 内容 |
|---|---|
| **数据来源** | `SetRecord`，`set_type != 'warmup'` |
| **单位** | kg |

#### 公式

```
容量(session)     = Σ( weight_i × reps_i )      对所有正式组 i
容量(exercise, 周) = 该周内该动作所有会话的容量之和
容量(周)          = 该周内所有正式组的容量之和
```

**自重动作的容量**：

```
容量 = Σ( 体重 × bw_factor × reps )
```

`bw_factor` 见 [REQUIREMENTS.md 3.4](./REQUIREMENTS.md#34-计量类型metric_type)。会话创建时快照当时的体重，保证历史容量可重算。

#### 边界情况

| 情况 | 处理 |
|---|---|
| 动作 `metric_type = 'duration'`（平板支撑） | **不计入容量**。时长无法折算成 `重量×次数`，单独统计总时长 |
| 动作 `metric_type = 'distance_duration'`（跑步） | 同上，单独统计距离与时长 |
| 用户体重未记录 | 自重动作**该次不计入容量**，并在图上标注缺口 |
| 单位偏好为 lb | 存储与计算一律用 kg，显示时换算 |

#### 什么时候不显示

- 该周期内无任何 `weight_reps` 或 `reps_only` 记录

---

### 4.2 肌群周组数

#### 定义

| 项 | 内容 |
|---|---|
| **回答的问题** | 我各肌群的训练量均衡吗？有没有明显偏废？ |
| **数据来源** | `SetRecord` JOIN `Exercise` 的肌群字段 |
| **单位** | 组数（sets） |

#### 公式

```
肌群周组数(muscle, week) = 该周内 primary_muscle = muscle 的正式组数
```

**次要肌群如何处理**：V1 **只计主要肌群**，避免一次卧推同时给胸、肩、三头各记一组导致重复计数。`Exercise` 保留 `secondary_muscles` 字段供 V2 使用。

**超级组的处理**：超级组只改变**执行顺序**，不改变计量。A1 做 3 组、A2 做 3 组，就是各记 3 组，与是否组成超级组无关。

### 4.3 图表规格 A —— 训练容量

| 项 | 规格 |
|---|---|
| **图表类型** | 折线图（周粒度聚合），配当前值的数字卡片 |
| **X 轴** | 周（周一起算），默认最近 12 周 |
| **Y 轴** | kg，**从 0 开始**（容量是累加量，0 有绝对意义） |
| **主序列** | 周总容量折线 |
| **辅助** | 4 周移动平均（容量周间波动大） |
| **下钻** | 点击某周可展开该周各动作的容量构成 |
| **训练总结中** | 单场容量 + 与上次同类训练的对比（±%） |

> **为什么 Y 轴必须从 0 开始**：容量是累加量。「8,000kg 和 8,500kg 的差别」只有从 0 起才看得出比例。这类图不从 0 开始会放大微小差异，制造虚假的进步感。
>
> **不要做单次训练的容量条形图**——单次噪声极大且没有参照系。用周粒度。

### 4.4 图表规格 B —— 肌群周组数

| 项 | 规格 |
|---|---|
| **图表类型** | 堆叠柱状图 |
| **X 轴** | 周（周一起算） |
| **Y 轴** | 组数，**从 0 开始**（这是计数，0 有意义） |
| **堆叠维度** | 肌群（胸/背/腿/肩/手臂/核心） |
| **参考带** | 10–20 组/周的水平阴影带（增肌推荐区间） |
| **默认范围** | 最近 12 周 |
| **可选切换** | 切到「肌群容量」视图——但**必须显示警告**：跨肌群比较容量会因重量差异而失真 |
| **手机端形态** | ⚠️ **改用横向条形图**：肌群名在左、柱向右延伸，一次显示一周（可左右切换周次） |

> **手机端为什么必须换图形**：6 个肌群 × 12 周的堆叠柱，在 360dp 宽的屏幕上每周只有 30dp——柱子细到看不出堆叠分层，肌群颜色也挤在一起。**横向条形图把分类轴放在纵向**，每个肌群独占一行，宽度充足，且肌群名称能完整显示（堆叠柱的 X 轴标签只能放缩写）。
>
> 这与「单序列」约束是同一个道理：**窄屏上要减少同一维度上的并行信息量。**

### 4.5 参考带的正确用法

10–20 组/周来自 Schoenfeld 等人的 meta 分析，是**增肌的推荐区间**。它不是及格线：

- 低于 10 组：可能刺激不足，但也可能是 deload 周或维持期
- 高于 20 组：收益递减，且恢复压力大
- **力量训练者（3–6 次大重量）需要的组数低于增肌者**，8–12 组/周也可能是合理的

**参考带是提示，不是评判。** 界面上不能出现「未达标」这类措辞。

### 4.6 边界情况

| 情况 | 处理 |
|---|---|
| deload 周 | 正常显示，但在 X 轴标注 deload 标记，避免用户误判为退步 |
| 某周完全没练 | 显示为 0 高度的空柱，不跳过（跳过会掩盖中断） |
| 一个动作涉及多个肌群 | V1 只计 `primary_muscle` |
| 用户自定义动作未标肌群 | 归入「未分类」，并提示用户补全 |
| 超级组 | 只改变执行顺序，不改变计量。A1 三组 + A2 三组就是各 3 组 |

### 4.7 必须搭配显示的指标

**训练量涨 ≠ 进步。**

无论是容量还是组数，上升都可能只是因为：休息变长、强度下降、动作变多、记录变松。

因此**容量图与组数图都必须与平均强度叠加显示**（平均 %1RM 或平均 RPE，折线叠加在柱状图上）。只有训练量和强度同向变化，才能判断是真的在进步。

### 4.8 什么时候不显示

- **容量图**：该周期内无 `weight_reps` / `reps_only` 记录时不显示
- **组数图**：数据 < 1 周不显示；1–3 周显示但标注「样本较少」

## 5. 训练频率

### 5.1 定义

| 项 | 内容 |
|---|---|
| **回答的问题** | 我坚持得怎么样？最近有没有断？ |
| **数据来源** | `WorkoutSession.completed_at` |
| **单位** | 次/周 |

### 5.2 公式

```
周训练次数(w) = 该周完成的会话数
连续周数(streak) = 从当前周往前，连续满足「周训练次数 ≥ 计划频率」的周数
```

### 5.3 为什么不用年视图日历热力图

**常见做法是 GitHub 风格的年度热力图。对本项目不适用。**

**数字**：3 次/周 × 52 周 = 156 次/年。365 − 156 = **209 天空白（57%）**。若按 53×7 = 371 格渲染，是 215 格空白。

**根因不是「空白多」，而是计量单位不匹配**：

热力图编码的是「**每天**练没练」这个二值量，而训练计划的单位是「**每周**练几次」。一个 3 次/周的计划，用户 100% 达标也只能填满 43%。**达标者的图看起来像失败。**

热力图适合「每天都在发生且应当每天都发生」的行为（如提交代码）。训练**本来就有休息日**，休息日是计划的一部分，把它渲染成空白等于把正确的事显示成缺失。

### 5.4 图表规格

| 项 | 规格 |
|---|---|
| **图表类型** | 周视图条带（每周一根柱）+ streak 数字 |
| **X 轴** | 周（周一起算），最近 26 周 |
| **Y 轴** | 训练次数，从 0 开始 |
| **达标高亮** | 达到计划频率的周用强调色，未达标的用中性色 |
| **计划线** | 水平虚线标注目标频率 |
| **streak 展示** | 大号数字显示连续达标周数 |

**年视图（可选，非默认）**：

如果提供年度总览，**空白天用中性灰，不用红色**。红色会把「休息日」编码成「失败」，而休息日是计划的一部分。

### 5.5 边界情况

| 情况 | 处理 |
|---|---|
| 当前周还没过完 | 当前周用半透明显示，不参与 streak 判定（避免周一就显示断连） |
| 计划中途变更频率 | 按当周生效的计划频率判定 |
| 临时训练（非计划内） | 计入训练次数 |
| 用户没有计划 | 不判定达标，只显示次数 |

### 5.6 什么时候不显示

- 无任何训练记录：显示空状态引导，不显示空图

## 6. 计划执行度

### 6.1 两个独立指标

| 指标 | 公式 | 回答的问题 |
|---|---|---|
| **出勤率** | `完成场次 / 计划场次` | 我**去**了吗？ |
| **符合率** | `Σ min(实际完成, 计划目标) / Σ 计划目标`<br>仅统计 `exercise_id` 匹配的组，分子做 clamp | 我**按计划练**了吗？ |

### 6.2 为什么必须拆成两个

用户临场调整是**正常的训练行为**，不是失败：

- 今天状态差，卧推减了 10kg
- 深蹲架被占了，换成腿举
- 感觉还有力气，多做了一组

合成一个指标会两边不讨好：
- 算进「完成」→ 掩盖了执行偏差
- 算进「未完成」→ 惩罚了合理的临场判断

**拆开之后语义清晰**：出勤率反映习惯，符合率反映执行度。**临场调整既不判失败，也不算满分。**

**分子 clamp 的必要性**：用户多做了一组，`实际 > 计划`。如果不 clamp，符合率会超过 100%，指标失去意义。`min()` 保证单次上限为 100%。

### 6.3 偏差标签

每场训练额外打一个标签，供用户回看：

| 标签 | 条件 |
|---|---|
| **按计划** | 动作、组数、次数全部匹配 |
| **修改** | 动作匹配，但组数/次数/重量有调整 |
| **替换** | 存在 `exercise_id` 不匹配的动作 |
| **临时** | 非计划内会话 |

### 6.4 图表规格

| 项 | 规格 |
|---|---|
| **图表类型** | 两个并排的环形进度 + 趋势折线 |
| **展示** | 当前周/月/计划周期的出勤率与符合率，各配一条历史趋势线 |
| **颜色** | 中性色为主。**不用红绿二元判断**，避免把「修改」渲染成错误 |
| **下钻** | 点击可查看偏差标签的分布 |

### 6.5 边界情况

| 情况 | 处理 |
|---|---|
| 计划场次 = 0（未设计划） | 不计算，显示「未设置计划」 |
| deload 周 | 该周不计入符合率统计 |
| 计划中途暂停 | 暂停期间不计入分母 |
| 计划周期未结束 | 分母只算已过去的计划场次 |

### 6.6 什么时候不显示

- 无计划：只显示出勤数（总训练次数），不显示比率

## 7. PR 看板

### 7.1 定义

| 项 | 内容 |
|---|---|
| **回答的问题** | 我哪些动作创过纪录？什么时候？ |
| **数据来源** | `PersonalRecord` |

### 7.2 PR 类型

| 类型 | 判定 |
|---|---|
| **最大重量** | 该动作历史上单组最大 `weight`（不限次数） |
| **最佳 e1RM** | 该动作历史上最大 `w × (1 + r/30)`，`r ≤ 12` |
| **最多次数** | 该动作历史上单组最大 `reps`（限同一重量档位内比较） |
| **最大容量** | 该动作单次训练的最大 `Σ(重量 × 次数)` |

> **四个 PR 分开记录，不合并成一个「最强」**。最大重量和最佳 e1RM 经常不在同一天产生（大重量低次数 vs 中等重量高次数），合并会丢信息。

### 7.3 图表规格

| 项 | 规格 |
|---|---|
| **形态** | 卡片列表，非图表 |
| **每张卡** | 动作名、PR 类型、数值、达成日期、距今天数 |
| **排序** | 按达成日期倒序（最近的在前） |
| **新 PR 提示** | 训练结束时，若本次刷新了 PR，在总结页突出显示 |

### 7.4 边界情况

| 情况 | 处理 |
|---|---|
| 首次记录即 PR | 标记为「首次记录」，用中性样式，不渲染成突破 |
| 同一数值多次达成 | 只保留最早一次 |
| 动作被删除 | PR 保留，标注「已停用动作」 |

## 8. 体重与力量双轴图

### 8.1 定义

| 项 | 内容 |
|---|---|
| **回答的问题** | 减脂期我掉的是脂肪还是肌肉？力量保住了吗？ |
| **数据来源** | `BodyMetric(weight)` + `SetRecord` 的 e1RM（用户选定动作） |

### 8.2 公式

左轴：体重 7 日移动平均（kg）
右轴：选定动作的 e1RM（kg），或**体重归一化 1RM**

### 8.3 图表规格

| 项 | 规格 |
|---|---|
| **图表类型** | 双 Y 轴折线图 |
| **左轴** | 体重（kg） |
| **右轴** | 选定动作 e1RM（kg）或相对 1RM |
| **动作选择** | 用户从常练动作中选一个（默认深蹲或卧推） |
| **切换** | 绝对 1RM ↔ 体重归一化 1RM |

**减脂期必须看归一化版本**：体重下降时，绝对 1RM 不变其实意味着相对力量**上升**了。只看绝对值会误判为「停滞」。

### 8.4 双轴图的注意事项

双轴图容易误导——两条线的相对位置取决于两个轴的范围怎么设，可以人为制造「交叉」的假象。

**缓解措施**：
1. 两个轴都用**独立的合理范围**，不手动调整
2. 明确标注左右轴各自对应哪条线
3. 轴线用与对应序列相同的颜色

### 8.5 边界情况

| 情况 | 处理 |
|---|---|
| 两个数据源时间不对齐 | 按各自实际时间取点，不强行插值对齐 |
| 体重数据缺失的区间 | 该区间不画体重线，力量线照常 |
| 选定的动作数据 < 2 点 | 提示「该动作数据不足，请选择其他动作」 |

## 9. 饮食记录（热量与蛋白质）

### 9.1 定义

| 项 | 内容 |
|---|---|
| **回答的问题** | 我吃够了吗？我的实际消耗是多少？ |
| **数据来源** | `NutritionLog`（每日两个数：总热量 kcal、蛋白质 g） |
| **单位** | kcal / g |

### 9.2 基础指标

```
热量达成率(d) = 实际摄入(d) / 目标摄入(d)
蛋白质达成率(d) = 实际蛋白质(d) / 目标蛋白质(d)
周达标天数 = 该周内达成率 ≥ 90% 且 ≤ 110% 的天数
```

**为什么达标区间是 90%–110% 而非「≥ 100%」**：热量摄入是估算值，本身有 ±10% 以上的误差。把「吃到 101%」判为超标是伪精确。**区间判定比阈值判定更诚实。**

### 9.3 TDEE 反推（核心价值）

```
实际 TDEE ≈ 平均每日摄入 − (Δ体重kg × 7700) / 天数
```

**推导逻辑**：体重变化反映的是能量收支差额。

- 体重**上升** 1kg（说明摄入 > 消耗）→ TDEE 应该**低于**平均摄入
- 体重**下降** 1kg（说明摄入 < 消耗）→ TDEE 应该**高于**平均摄入

所以公式里是**减号**。

**示例**：14 天平均每天吃 2400 kcal，体重从 75.0kg 降到 74.2kg（Δ = −0.8kg）

```
TDEE ≈ 2400 − (−0.8 × 7700) / 14
     = 2400 + 6160 / 14
     = 2400 + 440
     = 2840 kcal
```

即这位用户的实际消耗约 2840 kcal，而按公式估算可能只有 2500——**差了 340 kcal**。

### 9.4 使用 TDEE 反推的硬性前提

| 前提 | 说明 |
|---|---|
| **至少 14 天数据** | 天数太少，体重波动会淹没信号。**低于 14 天不显示该指标** |
| **体重必须用移动平均** | 用单日体重会得到荒谬的结果（见第 1.3 节） |
| **饮食记录要连续** | 记录天数 < 总天数的 70% 时不计算，提示「记录不完整」 |
| **体重测量条件一致** | 晨起空腹 vs 训练后混用会引入 1–2kg 噪声 |

> **7700 kcal/kg 是近似值**。脂肪组织并非纯脂肪（约 87% 脂质），且减重时会有水分与瘦体重的变化。这个系数在短期（2–8 周）估算里够用，**长期使用会漂移**。界面上必须标注「估算值，仅供参考」。

### 9.5 图表规格

| 项 | 规格 |
|---|---|
| **图表类型** | 双轴折线图（复用第 8 节的双轴模式） |
| **左轴** | 体重 7 日移动平均（kg） |
| **右轴** | 每日热量摄入（kcal），柱状图 |
| **参考线** | 目标摄入线（水平虚线）；反推的 TDEE 线（另一条虚线） |
| **读出** | 摄入线在 TDEE 线以下 → 在减重；两线距离 = 每日缺口 |
| **蛋白质** | 单独一张小图，实际 vs 目标 |

### 9.6 边界情况

| 情况 | 处理 |
|---|---|
| 记录天数不足 14 天 | 只显示摄入与目标的对比，**不显示 TDEE 反推** |
| 记录不连续（< 70%） | 提示「记录不完整，TDEE 估算可能不准」，仍显示但加警示 |
| 体重数据缺失 | 无法反推，提示用户先补体重记录 |
| 用户在增肌期 | 同样适用——公式对增重减重是对称的 |
| 单日摄入为 0（忘记记录） | **视为缺失，不参与平均**。用 0 填充会严重低估平均值 |

> **最后一条是最容易犯的错**：忘记记录 ≠ 没吃东西。把未记录的日子当 0 算进平均，会得到「平均摄入 1200 kcal」这种荒谬结果，进而推出完全错误的 TDEE。

## 10. 明确不做的图

| 图 | 不做的理由 |
|---|---|
| **3D 雷达图（肌群均衡度）** | 3D 透视会扭曲面积感知，读者无法准确比较；雷达图的面积随轴的顺序变化而变，同一个数据换个排序就是另一种形状。**改用 4.3 的堆叠柱状图。** |
| **饼图看肌群占比** | 人类对角度的判断精度远低于对长度的判断。且当分类 > 5 个时几乎无法比较。肌群正好是 6 个。**改用堆叠柱状图。** |
| **单次训练容量条形图** | 单次容量噪声极大（受当天状态、组间休息、动作顺序影响），且**没有参照系**——用户看到「本次 8450kg」不知道是好是坏。**改用周粒度的趋势图。** |
| **无移动平均的日体重折线** | 见 1.3。噪声大于信号，会诱发错误决策。 |
| **年视图日历热力图（作为默认视图）** | 见 5.3。计量单位与计划单位不匹配。可作为可选视图，但空白天必须用中性灰。 |
| **「训练得分」综合评分** | 把多个维度压成一个数字，用户无法知道**具体该改什么**。且权重怎么定都是拍脑袋。**保留分维指标，不做综合评分。** |
| **肌群恢复度估计** | 需要真实的恢复模型（涉及睡眠、营养、个体差异），现有文献不足以支撑一个可靠的算法。**给出伪精确的数字比不给更糟。** |
| **营养素占比饼图（碳水/蛋白/脂肪）** | 两个原因：① 同「饼图看肌群占比」，3–5 个分类的角度比较不可靠；② **V1 不做营养素细分**（见 [REQUIREMENTS.md 4.1](./REQUIREMENTS.md#4-范围与非目标)），没有数据可画。**改用堆叠柱或直接显示达标进度条。** |
| **单日热量摄入条形图** | 同「单次训练容量条形图」——单日噪声大（聚餐、忘记记录、估算误差），且没有参照系。**用周均值 + 目标线。** |
| **AI 输出的「训练评分」或「身体年龄」** | 把多维数据压成一个由模型生成的数字，用户无法知道**具体该改什么**，且模型的评分标准不可审计、不可复现。**AI 只做描述与解释，不做评分。** |

## 11. 实现注意事项

### 11.1 聚合查询的位置

| 场景 | 计算位置 |
|---|---|
| 图表数据 | **后端聚合**，返回已按时间粒度归并的序列 |
| 单次训练详情 | 后端返回明细，前端直接渲染 |
| 跟练中的实时容量 | **前端本地算**（数据已在本地 SQLite） |

后端聚合查询需要索引支撑：

```sql
-- 示意
INDEX idx_set_record_session (session_exercise_id, set_type)
INDEX idx_session_user_date (user_id, completed_at)
INDEX idx_body_metric_user_type_date (user_id, metric_type, measured_at)
```

### 11.2 口径变更的处理

**如果未来修改了某个指标的口径**（例如把容量从「仅正式组」改成「含热身组」）：

- 历史图表**必须用新口径重算**，不能新旧混用
- 因此**派生指标不入库**，或入库时带上口径版本号
- 这是 6.5 节 `SetRecord` 设计中「volume 是派生值」的原因

### 11.3 空状态

每个图表都必须设计空状态：

- **无数据**：引导用户去记录，不显示空图
- **数据不足**：显示已有部分 + 明确提示还缺什么
- **加载中**：骨架屏，不用转圈
- **加载失败**：显示重试按钮 + 错误原因
